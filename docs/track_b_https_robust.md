# 트랙 B HTTPS 입력 견고성 짝 비교 (로그 구간화·방향만)

[#35·#36](track_b_https_eval.md)에서 약했던 조건(날짜가 바뀐 시험, 처음 보는 피해자)이 입력 표현을 바꾸면 달라지는지 본 **탐색적** 후속이다. 시험 결과에서 약한 조건을 본 뒤 고른 것이므로 개선이든 악화든 독립 최종 검증이 아니다. 라벨은 캡처 단위 잠정 라벨이며, 토론 안건 4(11/4)의 합의 범위를 따른다.

## 조건

| 항목 | 내용 |
|---|---|
| 입력 | `logb`: 앞 k개 값만 `x=0이면 0, 그 외 sign(x)×(1+floor(log2\|x\|))`(구간 경계는 사전 고정, 나머지 칸은 0 패딩) / `dir`: 앞 k개 값의 부호. `dir`은 길이 의존성 진단이며 개선 입력으로 주장하지 않는다 |
| 고정한 것 | 분할(04-11↔04-16), 범위(all / only_242104), k=5·10·20·30, RF·LightGBM 설정, 시드 0·1·2, 시험 행 |
| 규모 | 신규 192회(입력 2종 × 방향 2 × 범위 2 × k 4 × 모델 2 × 시드 3). 원본은 다시 학습하지 않고 저장된 Colab 최종 결과(`track_b_https_eval_2026-11-04_colab`)와 같은 조건끼리 짝 비교 |
| 실행 | Windows 로컬, 커밋 `e760a2e`(깨끗한 트리), run-id `2026-11-04_v1`. 행별 예측 SHA-256 `0d1564a3eb8c9060f88c69cf6fab7d334fa143727a08e09f2f35cc2324e7477d`(Drive `predictions/track_b_https_robust_2026-11-04_v1`, gzip 사본 `ef1ce445…`) |
| 재현 | `uv run python -m src.track_b.https_robust --flows-run-id 2026-11-02_v1 --audit-run-id 2026-11-02_v2 --run-id <ID>` |

## 결과

원본 seq 대비 macro-F1 변화(3시드 평균 차이, RF):

| 분할 | 입력 | k=5 | k=10 | k=20 | k=30 |
|---|---|---|---|---|---|
| 04-11→04-16 전체 | logb | −0.020 | −0.001 | −0.001 | −0.001 |
| 04-11→04-16 .242.104만 | logb | −0.077 | −0.002 | −0.001 | −0.002 |
| 04-16→04-11 전체 | logb | −0.055 | −0.020 | −0.018 | −0.018 |
| 04-16→04-11 .242.104만 | logb | **+0.139** | **+0.175** | **+0.164** | +0.070 |
| 04-11→04-16 전체 | dir | −0.273 | −0.073 | −0.000 | −0.003 |
| 04-16→04-11 .242.104만 | dir | −0.364 | +0.064 | +0.160 | +0.081 |

LightGBM과 전 조건은 `paired_summary.csv`, 부분집합별 변화는 `paired_subsets.csv`.

1. **날짜가 바뀐 같은 피해자**(04-16→04-11 `only_242104`): `logb`에서 공격 recall이 k=5 0.50→1.00, k=10 0.50→0.99, k=20 0.53→0.99, k=30 0.73→0.94로 오른다. 04-11 공격은 첫 패킷이 304, 04-16 공격은 308처럼 몇 바이트씩 달라 원본 값으로는 겹침이 50%였는데, 구간화하면 같은 구간(256~511)에 들어간다. 이 설명은 입력을 바꾸면 recall이 오른다는 관찰과 부합하지만, 구간 효과만 분리한 통제 실험은 없다.
2. **처음 보는 피해자(.88.81)는 `logb`로 해결되지 않았다.** 04-11→04-16에서 .88.81 공격 recall이 `logb`는 모든 k·모델에서 0이다(원본 seq도 RF 0, LightGBM은 k=5 0.0003·k=20 0.0010). `dir`은 k=5에서 RF·LightGBM 모두 0.925로 오르지만 같은 조건 CSV 확인 정상의 specificity가 1.000→0.257로 떨어진다(오탐 급증, 모두 공격으로 판정하는 쪽에 가깝다). k=10·20·30의 `dir` .88.81 recall은 RF 0.0042·0.0067·0.0013, LightGBM 0.0127·0.0425·0.0046(3시드 평균)이다. 높은 공격 recall만으로 새 피해자를 해결했다고 해석할 수 없다.
3. **오탐이 늘었다.** `logb` k=5에서 CSV 확인 정상의 specificity가 1.000→0.973~0.982, CSV 미매칭 정상은 0.999→0.938(04-16→04-11 전체)로 떨어져 일부 조건의 macro-F1이 내려갔다. 값을 뭉갠 대가로 보인다. 확정한 원인은 아니다.
4. `dir`은 대부분 크게 나빠졌다(최대 −0.69). k=5에서는 정상 specificity가 크게 떨어지는 것이 주된 원인이다. 크기·길이 정보에 의존한다는 진단이다.

**.88.81 포함 대 제외 학습**(추가 학습 없이 기존 결과에서 계산, `scope_pair.csv`): 04-16→04-11에서 같은 시험 행의 .242.104 공격 recall이 seq 입력에서 포함 학습이 제외 학습보다 +0.27~+0.49(k별) 높았다. 이 대조는 학습 날짜 04-16과 시험 날짜 04-11을 고정하고 .88.81 공격 3,951행의 추가 여부만 바꾼다. 다만 공격 표본 수, 공격 패턴 다양성, 클래스 비율이 함께 바뀌므로 무엇의 효과인지는 분리하지 못한다. 04-11→04-16은 두 범위의 학습 데이터가 같아 차이가 0이다. `scope_pair.csv`의 `same_test_rows`는 두 범위의 시험 행 개수가 같은지만 비교한 것이다(행 ID 집합 동일성은 Codex가 원본 flows의 분할·행 ID 완전성 검증으로 따로 확인했다).

**정상 서버 겹침**(`benign_overlap.csv`): 학습·시험 날짜 사이에 정상 서버 282개가 겹치고(04-11 학습 655개·04-16 시험 1,374개), 시험 정상 플로우의 37%(04-11→04-16)와 43%(04-16→04-11)가 겹치는 서버로 간다. 서버 IP는 입력이 아니지만, 처음 보는 서버로의 일반화 주장은 하지 않는다. 겹침 감사는 서버 IP 기준이며, 합의한 세션(연결) 단위 겹침은 감사하지 않았다(세션 키 정의와 별도 집계 필요).

## 한계

- 시험에서 약한 조건을 보고 고른 후속이므로 같은 시험에서 좋아져도 탐색적 개선이다.
- 날짜·피해자 교락, 잠정 라벨은 그대로다. 공격 셀이 3개뿐이라 교차로 풀 수 없다.
- 개선은 한 조건(같은 피해자, 날짜 변화)에 한정되고, 오탐이 늘며, 새 피해자는 해결되지 않았다.
- 시간 간격(`t_k`), 잡음 증강, 조기 판정 곡선·임계값은 이번 범위 밖이다(후속 설계).
- Windows 로컬 실행 결과이다. Colab 재실행·Mac 재학습·pcap 재추출은 하지 않았다. Mac에서 저장 예측·집계를 독립 재계산해 일치를 확인했다(192회·예측 3,433,200행·부분집합 1,536·요약 64, 불일치 0).
- `https_eval.py`의 metadata 원본 SHA(`60dfedfd…`)는 PR의 LF 원본 SHA(`8ddee8292693759ae9b36e65e6ba4ee6c02fd8585c7ea1d25e4d20fcbc484dd0`)와 다르다. Windows 작업 트리의 CRLF 바이트 SHA이고, LF로 바꾸면 PR 원본과 일치한다(Codex가 반대로 PR 원본을 CRLF로 바꿔 일치를 확인했다). 실행 시점 파일의 원본 SHA는 metadata 그대로 유지한다.
