# B: 통제 수집 LAN 파일럿 1 결과 (안건 12, 2026-11-09)

사전 고정 문서 개정 4c 기준의 수집·매칭 점검용 파일럿이다. **학습·평가에 쓰지 않는다.** 점검 결과이며 모델 성능이 아니다. Codex 검토 전(Codex는 `fe2ac05` 코드 보완 확인 후 파일럿 착수에 동의, 합격 여부는 결과로 검토하겠다고 함).

## 환경
- 서버+캡처: 노트북(Windows 11, Wi-Fi `192.168.45.224`, Python 3.14.3, OpenSSL 3.0.18, requests 2.32.5/urllib3 2.6.3), dumpcap(Wireshark 4.6.4, Npcap 1.86) Wi-Fi 인터페이스, 서버 `--bind 0.0.0.0`, 서버 소켓 TCP_NODELAY. 방화벽: 인바운드 TCP 8443~8445를 데스크톱 한 대(`192.168.45.178`)에서만 허용하는 임시 규칙(Public 프로필).
- 클라이언트(러너): 데스크톱(이더넷 `192.168.45.178`, Python 3.11.2, **OpenSSL 1.1.1s**, requests 2.34.2/urllib3 2.8.0, curl 8.21.0 Schannel). `collect.py`는 노트북과 같은 파일(SHA-256 `ab3786f8507a28a20800efce299a6b7e1dcc2eb09f2f5c0a0f75bbef5bfd5dbd`, 커밋 `fe2ac05`의 내용). 데스크톱에는 git 저장소가 없어 메타데이터 `git_commit`은 null.
- 설정: 학습 3라운드, 시험 2라운드, `--wait-after 660`, `--pad 60`, 시드 11. 서버 3개는 인증서만 다른 포트 3개(S1 RSA-2048, S2 ECDSA P-256, S3 RSA-4096 2단 체인).
- 원본 보존: 노트북 `DATA_DIR/collect_pilot1/`(pcap, 서버 수락 로그, 러너 로그·attempts·meta(데스크톱에서 Drive로 받음), match 출력), 데스크톱 `C:\capstone-pilot\`, Drive `pilot1_desktop/`. 파일별 크기·SHA는 아래.

## 관측 (파일럿 한정, 탐색)
- **클라이언트 ClientHello(`seq_0`)**: requests 517, curl 391(구현 서명, 두 클래스에 같음). 서버 첫 비행(`seq_1`)은 S1 -1286, S2 -703~-705, S3 -1460(3세그먼트).
- **첫 요청의 위치(후보 방법 `first_req_idx`)**: 앞 5개 안에 들어온 비율은 **curl S1·S2 약 55~60%, requests S1·S2 99%, S3는 curl·requests 모두 0%**(S3는 서버 비행이 3세그먼트라 요청이 앞 5개 뒤로 밀림). 앞 10개 안에는 서버·구현 모두 100%. 한편 payload 패킷이 10개에 못 미치는 연결이 60/600(10%)이라 k=10에서 "미도달"로 분류된다(주로 로그인 시도 적은 짧은 에피소드). **loopback에서 본 "curl은 k=5에 요청이 들어오지 않는다"는 LAN에서는 틀린 가설이었다**(curl S1·S2에서 절반 이상 들어옴). 서버·구현에 따라 k=5의 정보량이 달라진다.
- **seq_0..4와 `first_req_idx` 범위에서는 클래스로 갈리는 길이·위치 단서가 보이지 않음**(아래 Opus 진단의 성공 응답 노출과 실패 전용 칸 고정은 이 범위 밖): `first_req_idx` 평균이 서버·구현별로 정상과 공격이 같고(예: curl S1 4.22 대 4.22), seq_0..4에서 한 클래스에만 나온 값은 건수가 한 자릿수(curl seq_3=199 공격 4건·정상 0건, requests seq_4=177 정상 1건)라 노이즈 수준이다. 표본이 작아(칸당 30연결) 결론을 내지 않는다.
- **Opus 검토 진단(2026-11-09, 정상 행·표본 작음·탐색)**: ① 정상 실패 전용 2/10이 (GET,4)·(POST,3) 두 칸에 고정돼 있어 "그 칸에서 실패로 끝나면 공격"이 배정표로 성립했다. 학습 단계로 RF를 학습해 시험 단계를 보면 공격 예측확률이 실패 전용 칸 0.45~0.56, 그 밖의 칸 0.88~0.98이고 정상 최대 확률을 넘는 공격 비율이 k=15 17.5%, k=20 42.5%, k=30 61.7%였다(지름길 진단이며 모델 성능이 아님). → 개정 5에서 9칸 회전으로 수정. ② 성공 응답(-152)이 앞 k개 안에 보인 정상 행 비율은 k=5에서 0, k=10에서 curl S1·S2 약 0.3·requests와 S3 약 0.1, k=15에서 0.3~0.4, k=30에서 약 0.7이고 공격에는 -152가 없다. ③ 데스크톱에 git이 없어 메타데이터 `git_dirty_src_tests=false`가 "깨끗함"으로 잘못 남았다(→ None으로 기록하도록 수정).
- 관측 대기시간(`t_k`): 중앙값 k=5 18ms, k=10 28ms(LAN, 파일럿).
- 성공/실패 응답 길이 단서와 실패 전용 부분집합 비교는 본 수집 이후 평가에서 본다.

## 이번 파일럿에서 고친 것·남은 것
- 고친 것: `payload>1448` 검사 임계값이 틀렸다(Windows는 TCP timestamps를 쓰지 않아 MSS가 1460). 1460으로 수정하고 보고서 항목 이름을 `flows_with_segment_over_mss`로 바꿨다. 파일럿 데이터로 다시 돌린 결과 초과 플로우 0개.
- 남은 것: Codex 검토(합격 여부), 본 수집(학습 30·시험 10라운드, 약 50분) 시작 전 방화벽 규칙 유지 승인, `w32tm /resync`(선택), 데스크톱 커밋 해시 기록(해시로 대체), 노트북 쪽 원본의 Drive 공유 승인.
