## 배경

캡디1은 "SII(IP·Port) 제거 → Shortcut Learning 방지 → 일반화 향상"을 핵심 기여로 내세웠으나, 같은 데이터를 무작위 80/20으로 나눠 평가해서 일반화를 **측정한 적이 없다**(`notebooks/models/baseline_rf.ipynb`의 `train_test_split`). 캡디2는 그 약속을 실증한다.

서술은 "오류 정정"이 아니라 최신 연구 흐름(엄격한 분포 이동 분할, Shortcut 방지 특징 설계, 불균형 대응 macro-F1)을 반영한 **심화 단계**로 한다.

## 트랙 A — Malicious_TLS

**포지셔닝**: 데이터셋 분석이 아니라 **B 시스템에 넣을 특징 구성과 모델을 고르는 검증 단계**. 보고서도 "이 실험으로 최종 시스템의 입력과 모델을 결정했다"로 서술한다.

**데이터**: 원본 CSV(`malicious_TLS.rar`)부터 다시 전처리한다. 캡디1은 극단값·중복 제거와 특징 선택 기준을 분할 전 전체 데이터로 산출해서 누수가 있었다. 모든 정제 기준과 스케일러는 **학습 셋에서만** 적합한다. 캡디1 정제본(`malicious_tls_cleaned.csv`)은 재현 비교용으로만 쓴다.

**클래스 구성 (모든 분류 실험에 동일 적용)**
- 원 구성 23종: 정상 1 + 악성코드 C&C 18종(TrickBot, CobaltStrike, Dridex, Qakbot 등) + 웹 취약점 스캐너 4종(burpsuite, nessus, arachni, golismero)
- **패턴 다양성 기준 18종 선별**: 그룹 분할 시 학습 또는 시험이 30행 미만으로 무너지는 5종(Shifu.A 2패턴, Banker 10, Drixed 29, Vawtrak.C 20, golismero 3) 제외. 제외 5종은 데이터 특성 절에서 따로 보고
- 18종 중 **5종을 미확인 위협으로 보류** → **13종(정상 1 + 악성 12) 학습**
  - 보류 5종은 두 계열에서 각각, 패턴 다양성이 중간인 것으로 선정: 스캐너 2(후보 nessus·arachni) + C&C 3(후보 Totbrick·Tiggre·TrickBot)
- 실험마다 분모가 다르면 체리피킹으로 읽히므로 모든 실험이 같은 18종을 쓴다
- 스캐너는 악성코드가 아니라 공격 도구 → 보고서에서 구분해 서술
- `Tor` 클래스는 익명화 네트워크 트래픽을 원 저자가 C&C 계열로 라벨링한 것 → 각주

**특징군 3개**
- 지문 9개: `tls_version`, `tls_cipher_suites_0~4`, `tls_chosen_cipher_suit`, 길이 2개
- 통계 78개: `IP_*` 39 + `payload_*` 39
- 시퀀스 30개: `0`~`29` = **처음 30개 페이로드 패킷의 길이, 부호가 방향**(+정방향 / −역방향). 캡디1 코드의 `bd_i = 바이트 차분값` 명명은 오류

**실험**
1. 특징군 비교: 전체 / 지문만 / 통계만 / 시퀀스만 (4조합)
2. 모델: Random Forest·LightGBM(기본선). **10/31 서은빈 확정: LSTM은 이번 필수 범위에서 제외하고, 1D-CNN은 B 첫 결과 이후 일정·비교 필요성에 따라 조건부로 진행**한다(시퀀스 입력만)
   - RF·LightGBM × 특징군 4 × 분할 2 × 시드 3 = 48회 / 환경. 이후 시퀀스 앞 k개 평가는 별도 36회 / 환경이며 기존 k=30의 sequence 12회를 재사용한다
3. 순서 섞기: 시퀀스 30개 순서를 무작위로 섞어 재학습 → 순서가 정보인지 직접 검증
4. 분할 2종 대조: [실험 1] 무작위 층화 분할 = 캡디1 방식 재현 / [실험 2] 시퀀스 패턴 그룹 분할 = 누수 통제. 주·보조가 아니라 대조 실험으로 서술
5. 미확인 위협 판정: 보류 5종을 시험에만 넣고 "미확인"으로 거절하는 비율 측정
   - 판정 기준: **Random Forest 예측 확률 최댓값 문턱을 우선**, 딥러닝은 비교 대상(소프트맥스는 미지 입력에 과신하는 성질이 있음)
   - 문턱은 학습 셋에서 다시 떼어낸 검증셋에서 "알려진 클래스 거절률 5%" 지점으로 고정
6. 해시 룰 기준선: 시퀀스 30개를 그대로 조회하는 무학습 기준선을 성능표 한 줄로 추가. 톤은 낮추되 감추지 않음
7. SHAP: 보조 시각화만. 특징 간 상관이 높아 SHAP 단독 해석은 신뢰도가 낮으므로 주 근거는 특징군 제거 실험
8. **10/31 추가: 초기 페이로드 패킷 수 평가 → 미확인 문턱 평가 순서**. 앞 k=5·10·20개만 보존하고 나머지 0 패딩, 기존 30차원·행·분할·모델 설정을 유지한다. k별 새 학습 36회, 원본 k=30과 비교한다. 접두 패턴 겹침·짧은 흐름의 건수와 비율 및 도달/짧음·접두 일치/불일치별 성능을 별도 보고한다. k=30은 짧은 흐름의 전체 시퀀스를 포함하는 최대 30개 입력이며 오프라인 분류 성능으로 해석한다. [코드 작성 전 실행 계획](sequence_prefix_plan.md). 계획 확인 전 구현·학습은 시작하지 않는다

**데이터 특성 (검증 완료 — 보고서 별도 절)**
- 시퀀스 패턴이 클래스별로 극히 고정적: 전체의 74.5%가 다른 행과 시퀀스가 동일. Shifu.A는 3,255행이 단 2패턴
- 정상과 악성의 시퀀스 패턴 겹침 0건 → 이 데이터에서는 해시 룰만으로 정상/악성 분리 가능
- 편중된 쪽은 악성이며 정상은 33,213행에 14,818패턴(44.6%)으로 다양함 → "데이터셋이 인위적"이 아니라 **악성 수집 방식(샌드박스 반복 실행)의 구조적 특성**으로 서술
- 같은 시퀀스 패턴이라도 나머지 88개 특징은 전부 다름(완전 중복 0행) → 통계·지문 모델에는 누수가 약함

## 트랙 B — HIKARI-2021

**탐지·분류 대상 4종 (+ 조건부 1종)**: 정상 / 정찰(Probing, CMS 취약점 스캔) / 침투(Bruteforce-XML, Bruteforce-HTTPS)
- L7 암호화 DoS는 **심화 확장 과제**: 수집 완료 시 5번째 대상으로 추가, 지연 시 4종 체계로 수행
- 웹 공격 생애주기(정찰 → 침투 → 마비) 구도로 서술

**서사 2단계 분리 (심사 방어)**
- **학술 실증**: 짝 데이터가 있는 Bruteforce-XML(04-12 ↔ 04-17)로 5일 간격 양방향 시간 분할 검증(HTTPS도 04-11 ↔ 04-16 짝이 있으나 피해자가 달라 보조 검증으로 둔다). 식별자 완전 배제 상태에서 캡디1 한계 대비 시간 분할 성능과 한계를 평가
- **실무 PoC**: 다중 분류와 조기 탐지. 시간 분할 짝이 없는 공격이 섞이므로 PoC로 한정해 주장하고 학술 실증 결론과 섞지 않음

**데이터**

| 공격 | pcap | 공격자 → 피해자 | 상태 |
|---|---|---|---|
| Bruteforce-XML | 04-12(271MB), 04-17(644MB) | .23 → 128.199.242.104:443 | 확보 |
| Bruteforce-HTTPS | 04-11(712MB), 04-16(5,352MB) | 04-11: .23 → 128.199.242.104:443 400개. 04-16: .23 → 128.199.88.81:443 3,951개 + .23 → 128.199.242.104:443 1,535개 | 확보·추출 완료 (md5 Zenodo 일치) |
| Probing (SCANCMS) | 05-02 중 1개(2.3GB) | .150 → 128.199.242.104:443 | 미확보 |
| L7 암호화 DoS | 로컬 자가 수집 | 로컬 HTTPS 서버 대상 | 조건부 |

- **10/31 정정 (HTTPS)**: 공식 Zenodo 레코드(5199540)의 Bruteforce-HTTPS pcap은 04-11(712MB)과 04-16(5,352MB) 두 개이며 둘 다 받아 md5를 확인하고 B 추출기로 443 플로우를 만들었다(04-11 4,596개, 04-16 33,560개). 위 표의 128.199.88.81 대상은 04-11에 **0개**이고 04-16에 3,951개(CSV와 같은 수)다. 공격 플로우는 04-11 400개, 04-16 5,486개이며 합 5,886개로 CSV Bruteforce 5,884건과 같지 않고 2개 차이다. 04-16 .242.104 중 페이로드 0개 플로우가 정확히 2개라는 사실은 확인했으나, 이 2개가 차이를 설명한다는 것은 **추정**이다. 공통 피해자는 .242.104뿐이다
- **HTTPS 공격 길이**: 04-11 .242.104는 페이로드 45~198개(중앙값 52), 04-16 .88.81은 8~228개(중앙값 22, 20개 이상 52%, 30개 이상 35%), 04-16 .242.104는 0~65개(중앙값 53). XML(12개 이하)과 달리 k=20·30에서 도달/짧은 흐름이 실제로 갈린다
- **라벨 (HTTPS)**: 캡처 규칙 "공격자(.23) → 피해자(.88.81/.242.104):443 = 공격, 그 밖의 443 = 정상"을 적용한 **캡처 규칙에 따른 잠정 라벨**이다. 피해자 대상 플로우 수가 CSV Bruteforce 건수와 거의 같고(04-16 .88.81은 3,951 = 3,951) 피해자 대상 플로우는 모두 CSV에 (IP·포트·피해자)가 같은 Bruteforce 행이 있다(.88.81 3,951/3,951)는 관찰에 근거하지만, 총수 근접만으로 규칙이 입증된 것은 아니다. 정상 쪽은 확인/미확인 분모를 나눠 보존한다: 04-16 비피해자 443 28,074개 중 CSV 정상 행과 대조된 것은 **23,944개**(CSV 행 23,951개 = Benign 23,950 + Background 1, 7개 플로우가 CSV 행 2개에 걸림), **미확인 4,130개**. 04-11 비피해자 4,196개 중 CSV 정상 대조 1,346개, 미확인 2,850개. 미확인은 정상 확인이 아니므로 평가는 "확인 가능 범위"와 "잠정 라벨 전체"를 모두 보고한다. 같은 4튜플에 CSV Benign 행이 함께 걸리는 현상(포트 재사용 가능성)과 지속시간이 약 28ms 어긋나는 현상(Zeek와 추출기의 시작점 차이 가능성)은 관찰이며 원인은 입증하지 않았다. .23 → .242.104의 CSV `Benign`이 6,794건 있어 **CSV만으로 IP 쌍 라벨링은 안 된다**. pcap↔CSV 대조는 지속시간 10ms 대신 4튜플에 페이로드 패킷 수 일치(.88.81 3,797/3,951)를 보조로 쓴다. 공격 쪽 매칭 모호성의 대칭 감사는 평가 전에 한다
- **시간 분할 주의 (HTTPS)**: 04-11 ↔ 04-16 짝이 있어 양방향 시간 분할이 가능하지만, .88.81은 04-16에만 있어 날짜 차이와 피해자 차이가 섞인다. .242.104만의 대조(공격 400 vs 1,535)를 함께 본다. 04-16 공격 행의 앞 k개 패턴 중 04-11 공격 패턴과 겹치는 비율은 k=5 27.9%, k=20 11.0%, k=30 0.1%이고 공격↔정상 접두 겹침은 0~1.4%다
- XMRIGCC 클래스는 포트 137/138(NetBIOS 평문)이라 제외
- HIKARI CSV는 Zeek FlowMeter 계열 피처이고 타임스탬프가 없어, 시간 분할과 조기 탐지는 pcap에서 직접 추출해야 한다

**라벨 규칙 (검증 완료)**: **캡처 파일이 곧 공격 유형**. 각 캡처에서 해당 공격자↔피해자:443 = 그 공격, 같은 캡처의 다른 443 = 정상
- 근거: XML 캡처 2개의 공격 플로우 1,216 + 3,925 = 5,141 = CSV의 Bruteforce-XML 총계와 정확히 일치
- CSV 전체에서 (출발지, 목적지, 포트)로 라벨링하면 정밀도 0.32 — 여러 캡처가 섞여 있기 때문. 캡처 단위로는 깨끗함
- 정상은 **같은 캡처 안의 비피해자 443 플로우**에서 가져온다(페이로드 보유 → "정상 쪽만 지문 없음" 누수 회피)

**추출기**: 자체 파서(표준 라이브러리). 644MB pcap에서 플로우 조립·TLS SNI 추출 동작 확인
- 산출 특징: 통계 / 시퀀스 (A와 같은 정의)
- **식별자 격리**: IP·포트·SNI·JA3는 별도 컬럼으로 보관하되 기본 모델 입력에서 제외
  - SNI는 라벨 생성에 쓰이므로 피처로 쓰면 정답 누출 → 대조 실험에 넣어도 "성능 상한선 참고치"로만 해석
  - JA3도 제외: HIKARI 공격은 단일 도구 산출물이라 JA3가 사실상 공격자 식별자. "지문 vs 행위" 질문은 A가 담당
- **1회 순회 체크포인트**: pcap을 한 번 읽는 동안 플로우별 5·10·20번째 패킷 시점의 누적 통계를 저장
- 플로우 타임아웃, 재전송 처리 기준을 코드에 명시

**L7 DoS 자가 수집 시 필수 설계**
- CIC-IDS2018 활용안은 폐기: 해당 Slowloris는 평문 HTTP라 443 구간이 없고, 원본 pcap이 수백 GB
- 자가 수집은 환경이 HIKARI와 달라 "캡처 환경 = 정답"이 될 위험이 있으므로:
  1. 같은 로컬 환경에서 정상 HTTPS 트래픽도 함께 캡처
  2. 환경 교차 실험(로컬 학습 → HIKARI 시험, 역방향). 성능이 무너지면 "환경을 외웠다"는 증거로 그대로 보고
  3. DoS 성능은 PoC로만 주장
- 로컬 폐쇄망의 자체 웹서버 대상으로만 수행(외부 대상 공격 없음)

**실험**
1. 다중 분류: 4종(또는 5종), 무작위 분할, macro-F1
2. 시간 분할 양방향: XML 04-12 학습 → 04-17 시험, 그리고 역방향
3. SII: IP·포트 포함 vs 제거 비교
4. 조기 탐지: 패킷 수 축 — 앞 5 / 10 / 20 / 전체
   - 조건부: L7 DoS 수집 성공 시에만 경과 시간 축(1초 / 3초 등) 추가. Slowloris는 느린 공격이라 패킷 수 축만으로는 조기 탐지를 주장할 수 없음
5. 환경 교차: L7 DoS 자가 수집 시에만

## 검증 방법

- 시퀀스 해석: 5개 항등식 100% 일치 재현(비영칸수=패킷수, 양수칸수=fwd패킷수, 음수칸수=bwd패킷수, 양수최대=fwd최대길이, 양수합=fwd총바이트)
- 추출기: HIKARI CSV와 같은 플로우의 통계 분포 대조
- 라벨: 두 XML pcap의 공격 플로우 합이 5,141인지 assert
- 미확인 위협: 보류 5종이 학습 셋에 0건인지 assert
- 그룹 분할: 같은 시퀀스 패턴이 학습·시험에 동시에 없는지 assert

## 알려진 한계 (보고서에 명시)

- B의 정상 비교군이 외부 웹서비스라 피해자 사이트만 두드리는 공격과 패턴 차이가 커서 과제가 쉬울 수 있음 → F1이 포화되면 혼동 행렬로 난이도를 정직하게 보고, 필요 시 정상군을 유사 HTTPS 세션으로 좁힘
- HIKARI는 단일 테스트베드, 공격자 IP가 각 1개 → 일반화 주장의 범위를 제한
- 두 날의 공격 패킷수 분포가 거의 같음(중앙값 27) → 시간에 따른 성능 저하가 작게 나올 수 있음
- HIKARI 배경 트래픽에 저자가 인정한 소량 오염
- 암호화된 DoS·DDoS를 담은 공개 데이터셋이 없음 → 캡디1 계획서 배경에 언급된 항목이므로 사유 명시
