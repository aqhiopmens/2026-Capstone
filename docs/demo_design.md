# 시연·대시보드 구상 (재생형 PoC, 고정 k=10) — 개정 초안

2026-11-10 개정(Codex·Astra 합의 방향 반영, 김강민 최종 확인 전). **구현·검증 전의 설계이며 일정은 11/8~11/14 시스템 통합**이다. 제출 계획서의 "시연 대시보드 개발"(3단계)과 `docs/plan.md`의 "pcap 업로드형 Streamlit, 로컬 실행"을 구체화한다. 실시간 캡처·자동 차단은 범위 밖이다. 이전 초안(11/8)의 5→10→15→20→30 단계적 판정은 **이번 제출에서 구현하지 않고 후속**으로 둔다(검증 폴드 설계·누적 FPR 목표가 확정되지 않았다. `track_b_collect_prereg.md` 4.4).

## 발표 메시지 (약 3분)
**"pcap을 올리면, 연결마다 앞 10개 payload 패킷만 보고 판정한 결과와 그 한계를 보여주는 재생형 시연."** 연구의 중심은 환경 변화에 따른 조기 탐지 성능과 한계 검증이고, 대시보드는 검증된 범위를 시연하는 장치다(과제명은 바꾸지 않고 보고서의 연구 초점 문구로만 쓴다. 최종 이행 기준은 지도교수님께 확인).
> "이 시연은 저장된 pcap을 재생해 연결마다 앞 10개 페이로드 패킷으로 판정합니다. 학습에 없던 공격이나 새 피해자에 대한 탐지를 보증하지 않으며, 그 한계는 평가 요약에 함께 표시했습니다."

## 선택한 범위 (Codex 합의, 김강민 확인 대기)
- **모델**: HIKARI 4클래스 RF(정상 / Probing / Bruteforce-XML / Bruteforce-HTTPS), 입력은 앞 k=10개 payload 패킷 길이(`seq`). k=10은 "k=5가 더 나빠서 골랐다"는 최적화 주장이 아니라 **기존 계획의 고정 관측량 중 제출용 대표 시연값**으로 선택했다. k=10도 XML·서버 단서가 자동으로 제거되는 것은 아니다. k=5·20 등 기존 평가 결과는 보고서에 유지한다.
- **통제 수집 이진 모델은 시연에 넣지 않는다.** 서버 구성 3개·공격 1종의 탐색적 결과라 화면에서 일반 탐지로 오해될 수 있어 보고서의 별도 보완 실험으로 둔다(`track_b_collect_eval.md`).
- **10개 미만 연결**: 판정 시점에 "10개 미도달"로 표시하고, 실제 연결 종료를 확인한 뒤에 0 패딩으로 분류한 결과를 보여준다(10개 관측 후의 조기 판정과 구분). 캡처가 중간에 끊긴 연결은 실제 종료와 구분해 표시한다.

## 사용할 모델 (평가 ID·입력·클래스 순서, Codex 요청으로 고정)
- **평가 ID**: `track_b_four_class_2026-11-08_v2`(결과 `outputs/results/track_b_four_class_2026-11-08_v2/`, 저장 예측 `DATA_DIR/predictions/track_b_four_class_2026-11-08_v2/predictions.csv.gz`·`holdout_predictions.csv.gz`, 설명 `docs/track_b_four_class.md`). 이 실행의 `code_sha256`(`src/track_b/four_class.py` `7fdc6790…`)이 `b/four-class` 브랜치 `9f80a0e` 이후의 파일과 같고, 행별 예측을 저장했으므로 재학습 예측과의 일치 확인에 쓸 수 있다. 첫 실행 `..._v1`(코드 `19806fd`, SHA `2097b7f6…`, Python 3.12.14)과 주 결과(RF `seq` k=10 전체 시험 macro-F1 0.8449)는 같지만 환경이 달라(v2는 Python 3.14.3) 문서에서 섞어 인용하지 않는다. 두 실행의 메타데이터에는 `git_commit`·`machine`이 비어 있다.
- **입력**: 원본 `seq`, k=10 — 연결의 처음 30칸 구조(`seq_0..seq_29`)에서 앞 10칸만 남기고 나머지는 0(부호 = 방향, 길이 = 페이로드 바이트, 값이 없으면 0 패딩). 앞 3칸 마스킹(`seq_mask3`)은 비교·한계 설명에만 쓴다. **원본 입력을 쓴다고 쉬운 구분 단서(도구·서버·캡처) 문제가 해결된 것은 아니다.**
- **클래스 순서**: `benign, probing, bruteforce_xml, bruteforce_https`(`CLASSES`)는 **화면 표시·혼동 행렬의 순서**다. **확률 열은 `model.classes_`(사전순)를 따른다**(아래 "구현 전 확정 3항목" 1). 분류는 `predict_proba` argmax(동률은 `model.classes_` 순서).
- **모델·시드**: RF(`make_model("rf")`, 100그루, `class_weight="balanced"`). 평가는 시드 0·1·2의 평균이다. **시연 모델은 시드 0으로 고정**한다. 성능을 비교해 고른 것이 아니라 미리 정한 대표 실행이다.
- **점수 표시 구분**: 시연 모델에는 **검증한 시드 0의 성능**을 연결하고, 기존 3시드 평균은 평가 요약으로 별도 표시한다. 시연용으로 **재학습하면 항상 새 평가 ID**로 기록하고, 같은 행의 예측이 기존 저장 예측과 같음을 확인했을 때만 기존 점수를 출처와 함께 인용한다(다르면 새 ID로 다시 측정하고 기존 점수를 붙이지 않는다).
- **학습 자료**: HTTPS 04-11, XML 04-12, Probing 캡처 앞 70%(종료 ≤ T), 정상은 각 캡처의 비피해자 443 플로우. 시험: HTTPS 04-16, XML 04-17, Probing 뒤 30%. **알려진 한계**: 새 피해자 .88.81의 공격은 전부 정상으로 판정(recall 0), 캡처 단위 잠정 라벨(Probing은 CSV로 확인 불가), 공격 유형마다 도구·서버·캡처가 하나씩이라 유형 구분과 캡처 구분이 분리되지 않음, k=10에서 학습에 없던 공격 유형의 경보율은 0.

## 구현 전 확정 3항목 (Codex)
1. **확률과 공격 유형의 연결**: 화면은 모델이 내놓는 확률의 열을 **`model.classes_`로 확인해** 클래스 이름에 연결한다. 위 `CLASSES` 순서(`benign, probing, bruteforce_xml, bruteforce_https`)와 같다고 가정하지 않는다. 실제로 scikit-learn은 `classes_`를 사전순(`benign, bruteforce_https, bruteforce_xml, probing`)으로 정렬하므로 순서를 가정하면 공격 유형이 잘못 표시된다. 테스트: `classes_`를 기준으로 열→이름 매핑을 만들고, 평가 경로의 argmax 결과와 대시보드 경로의 판정이 같은지 확인한다.
2. **재학습은 항상 새 평가 ID**: 시연용으로 새로 학습한 모델은 새 ID로 기록한다. 같은 행의 예측이 기존 저장 예측(`..._v2`)과 같음을 확인했을 때만 기존 점수를 출처(평가 ID·시드 0)와 함께 인용한다.
3. **구현 시작 코드 버전**: 문서 브랜치(`docs/demo-design`)에는 `four_class.py`가 없다. 구현 브랜치는 **`b/four-class` 브랜치의 `a234bf0`(평가 코드가 있는 정확한 커밋)에서 만들고** 이 시연 문서(`aaa6dc2` 이후)를 가져온다. 구현 코드는 문서 확정 뒤 별도 브랜치에서 진행한다.

## 화면 4개 (최소 구현)
1. **자료 선택**: pcap 파일, 검증된 모델(4클래스 RF, k=10 고정). "저장된 pcap 재생"임을 상단에 표시. 실험용 정답 라벨은 **평가 화면에만** 쓰고 모델 입력에서 제외한다.
2. **연결 목록**: 연결별 상태(10개 관측 후 판정 / 10개 미도달·종료 후 0패딩 분류 / 캡처 절단), 판정 클래스와 확률, 관측 대기시간(연결 시작 → 10번째 payload 패킷, 원래 패킷 시각 기준). 재생 속도를 바꿔도 대기시간은 바뀌지 않는다.
3. **연결 상세**: 앞 10개 패킷 길이·방향 그래프, 4클래스 확률, 판정 결과, 관측 대기시간. 앞 10개 이후의 패킷은 모델 입력에 쓰지 않으며 화면에서도 "판정 이후 관측"으로 구분한다.
4. **평가 요약(정답 있는 자료에서만)**: 클래스별 재현율·정밀도와 혼동 행렬, 정상 오탐 건수/분모, 10개 미도달 비율, pcap 처리시간·모델 추론시간(관측 대기시간과 별도). **오탐·미탐도 그대로 보여 준다.** 표지에 "검증된 4클래스 범주이며 미학습 공격·새 피해자에 대한 탐지 보증이 아님"(예: .88.81 recall 0)을 표시한다.

## 지켜야 할 조건 (Codex·Astra 완료 조건)
1. **평가 모델과 시연 모델의 일치**: 특징 순서(`seq_0..seq_29`)·클래스 순서·마스킹/패딩 규칙을 모델 메타데이터에 기록한다. 같은 자료를 평가 경로(`four_class.py`)와 대시보드 경로에 넣었을 때 **입력과 예측이 같은지** 테스트한다. 모델을 다시 학습했다면 기존 평가 점수를 그대로 붙이지 않는다(저장된 행별 예측과 재학습 예측이 같음을 확인한 뒤에만 기존 점수를 인용).
2. **판정 시점의 정확성(미래 정보 차단)**: 10번째 payload 패킷까지의 정보만 쓴다. 패킷 수·통계·종료 여부 등 **모든 입력**을 그 시점까지로 계산한다(`payload_packets`는 판정 입력에 들어가지 않는다). 같은 앞 10개에 서로 다른 뒷부분을 붙여도 입력·예측이 같은지 보는 **누수 불변성 테스트**를 별도로 유지한다. `test_sha`(시험 행 동일성)는 이 검사를 대신하지 않는다.
3. **경보 조건은 사전 고정값만**: 고정 k 분류는 `predict_proba`의 argmax(동률은 `model.classes_` 순서)를 그대로 쓴다. 시연용 임의 임계값 금지. 이때의 FP는 관측값이며 누적 FPR 목표를 달성한 결과가 아니다.
4. **시연 자료**: 학습·임계값 선정에 쓰지 않은 시험 자료여야 한다. **시연 사례를 고른 기준과 전체 시험 성능을 화면에서 구분**하고, 시연 자료의 점수를 연구 전체 성능처럼 설명하지 않는다. 성공 사례만 고른 재생과 전체 평가를 섞지 않는다.
5. **재생 모드와 처리 성능**: 화면에 "pcap 재생이며 실시간 운영 지연이 아님"을 명시한다. 10MB 30초·플로우당 10ms는 프로그램 처리 성능이고 관측 대기시간(`t_k10`)과 구분한다. 기존 측정(`docs/track_b_perf.md`: Windows 통과, Colab RF 단건 p95 10ms 초과)은 측정 조건과 함께 적고 최종 통합 프로그램에서 다시 확인한다.
6. 정답 라벨, 서버·IP, 실험 메타데이터는 모델 입력과 화면 설명에서 분리한다.

## 시연 pcap 선정 규칙 (2026-11-11 고정, 새 파일의 예측을 보기 전)
시험 캡처 세 개(HTTPS 04-16, XML 04-17, Probing `Sunday_2021-05-02_1206.pcap`)마다 **시험 구간의 시작점**부터 같은 크기 N MiB를 패킷 경계에서 잘라 쓴다. 시작점은 HTTPS·XML은 파일 처음, Probing은 4클래스 분할의 시험 시작 시각 `T+600초`(`probing_boundary_ts`+600)다. **N은 모델 예측을 보지 않고 라벨 구성만으로 정했다.** 후보 {10, 20, 30, 64, 100} MiB 중 세 파일 모두에 해당 캡처의 시험 클래스(HTTPS는 학습에 있던 피해자 .242.104와 새 피해자 .88.81 각각)가 10개 이상 들어가는 최솟값인 **64 MiB**다(HTTPS 04-16 앞 64 MiB: 정상 450·.88.81 82·.242.104 16, XML 04-17: 정상 420·XML 180, Probing 시험 시작점부터: 정상 77·probing 992, 라벨만 사용한 사전 계산). 두 피해자의 공격이 04-16 전체에 섞여 있어 시간 구간으로 나누는 규칙은 성립하지 않는다.
- **이력(먼저 본 결과)**: 처음 만든 HTTPS 앞 10 MiB(`https_0416`, 알려진 피해자 공격 0개, 새 피해자 공격 14개 전부 정상으로 판정, recall 0)를 먼저 확인했다. 그 뒤 위 규칙으로 64 MiB를 정해 새 파일의 예측을 보기 전에 고정했다. 10 MiB 결과는 버리지 않고 기록에 남기며, 64 MiB 파일은 "시연을 위해 추가로 구성한 사례"로 표시한다.
- **채점 가능 수 확인**: 라벨이 10개 이상 들어 있다는 것과 실제로 10개 이상 채점할 수 있다는 것은 다르다. 새 예측을 보기 전에 그룹(HTTPS는 피해자별)마다 유일 매칭·입력 일치·중간 시작·짧은 연결의 종료 증거를 집계해 실제 채점 가능 수를 먼저 낸다.
- **대응표**: 학습·제외 행이 정답으로 채점되지 않도록 대응표는 평가 코드의 `part == "test"` 행으로만 만든다. 원본 `seq_0..9`를 함께 저장해 "매칭됐지만 입력이 다른" 연결은 채점에서 빼고 건수를 표시한다.
- **표시**: 시연 화면의 채점은 이 잘린 파일의 관측값이며 전체 시험 성능(평가 ID `track_b_four_class_2026-11-08_v2`)과 구분한다. HTTPS는 피해자별(.242.104 / .88.81) 재현율을 따로 보이고, 새 피해자 .88.81은 평가 전체와 마찬가지로 정상으로 판정되며 한계 사례로 따로 표시한다.
- **환경**: 모델은 scikit-learn 1.8.0·Python 3.14.3에서 학습했다. 환경이 다르면 로드를 거부하고 녹화는 이 환경으로 고정한다.

## 구현 순서 (제안)
1. 모델 저장·메타데이터(평가 결과와 연결되는 모델·특징·클래스 정의) + 평가-시연 입력·예측 일치 테스트

3. 화면(자료 선택 → 연결 목록 → 연결 상세 → 평가 요약), 누수 불변성 테스트 유지
4. 시연 pcap 선정·영상 녹화(11/8~11/14 일정). 시연·녹화 기계는 김강민 노트북으로 고정.

## 미결
- 시연 모델 저장 위치. 입력(원본 `seq`)과 시드(0)는 확정(Codex 합의, 김강민 확인). 구현 코드는 문서 확정 뒤 별도 구현 브랜치로 나눈다.
- Probing의 잠정 라벨 표시 방식(시연 pcap 선정 규칙은 위에서 고정).
- 단계적 정책(5→30)은 후속. 실시간 대시보드가 되면 "분석 중"이 무한히 남지 않도록 유한한 시간 제한이 필요(`track_b_collect_prereg.md` 4.4).
- 교수님 평가 기준 충족 여부는 AI 합의가 확정할 수 없으므로 사람이 확인할 항목이다.
