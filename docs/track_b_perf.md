# B: 계획서 성능 목표 측정 (10MiB pcap 처리 시간, 플로우 1건 판정 지연)

계획서 최종목표의 "10MB 규모 pcap 30초 이내 처리, 플로우 1건당 판정 지연 10ms 이하"를 재었다(정확도는 재지 않음). 설계는 Slack 안건 7에서 결과를 보기 전에 고정했다.
코드 `src/track_b/perf_measure.py`, 결과 `outputs/results/track_b_perf_2026-11-05_win_v1/`. **Windows 측정만 완료**(kyle-win, Intel 8코어, Python 3.12.14, scikit-learn 1.6.1, lightgbm 4.6.0, 깨끗한 커밋 `d9fc58c`). Colab 측정은 별도 실행 예정이고 시간 값은 환경 의존이다.

## 정의
- 모델: 2021 04-11 HTTPS(payload>0) 학습, RF 100그루·LightGBM 고정 설정, 시드 0, k=5·10, 입력 seq. 모델 학습은 측정 구간 밖.
- 목표 1: 각 pcap 앞부분을 패킷 경계에서 10MiB 이상이 되는 첫 지점에서 자른 시료 3개에 대해 [pcap 읽기·플로우 조립 + 앞 k개 특징 생성 + 전체 플로우 일괄 판정] 벽시계 시간. 워밍업 1회 뒤 5회. 판정 = 시료별 5회 최댓값 ≤ 30초(중앙값은 참고).
- 목표 2: 앞 k개 페이로드 패킷이 도달한 플로우 하나의 [특징 벡터 생성 + 단건 predict(n_jobs=1)]. 패킷 도달 대기와 pcap 파싱은 제외하고 따로 적는다. 도달 플로우가 1,000개 미만이라 3개 시료의 전수를 썼다. 판정 = p95 ≤ 10ms, 최댓값·10ms 초과 건수 기록.

## 한계
- 시료가 3개 pcap의 앞부분 10MiB뿐이고 플로우 수가 81~133개로 적다. 플로우가 많은 트래픽에서는 시간이 달라질 수 있다(10MiB 안의 구성에 의존).
- 끝에서 잘려 종료되지 않은 플로우가 많다(41·69개). 앞 k개 판정에는 영향이 작지만 플로우 전체 통계에는 쓸 수 없다.
- 단건 시간은 DataFrame 생성을 포함한 파이썬 호출 지연이며 서비스 지연(대시보드·네트워크·직렬화)은 측정하지 않았다. Windows 한 대, 한 번의 실행이다.
- 단일 코어 n_jobs=1 기준이며 병렬화나 경량화 개선은 하지 않았다. 계획서 목표는 이 조건에서 모두 충족했다.
