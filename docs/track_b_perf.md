# B: 계획서 성능 목표 측정 (10MiB pcap 처리 시간, 플로우 1건 판정 지연)

계획서 최종목표의 "10MB 규모 pcap 30초 이내 처리, 플로우 1건당 판정 지연 10ms 이하"를 재었다(정확도는 재지 않음). 설계는 Slack 안건 7에서 결과를 보기 전에 고정했다.
코드 `src/track_b/perf_measure.py`, 주 결과 `outputs/results/track_b_perf_2026-11-05_win_v2/`. Windows(kyle-win, Intel 논리 CPU 8개, Python 3.12.14, 깨끗한 커밋 `17749fb`)와 Colab(CPU 2026.07, 논리 CPU 2개, Python 3.12.13, 소스 묶음 `676835d`)에서 측정했다. 시간 값은 환경 의존이다.
v1(`..._win_v1`)은 조립 1회를 8개 조합에 재사용하고 단계 시간을 더한 값이라 합의한 연속 측정과 달라 진단으로만 남겼다(범위 0.072~0.107초).

## 정의
- 모델: 2021 04-11 HTTPS(payload>0) 학습, RF 100그루·LightGBM 고정 설정, 시드 0, k=5·10, 입력 seq. 모델 학습은 측정 구간 밖.
- 목표 1: 각 pcap 앞부분을 패킷 경계에서 10MiB 이상이 되는 첫 지점에서 자른 시료 3개에 대해, 조합(모델·k·n_jobs)마다 **[파일 읽기 시작 → 플로우 조립 → payload 필터 → 특징 생성 → predict 종료]를 하나의 연속 타이머**로 잰다. 워밍업 1회 뒤 5회. 판정 = 시료별 5회 최댓값 ≤ 30초(중앙값은 참고). 단계별 시간(`runs.csv`)은 같은 실행의 체크포인트 차이로 진단용이다.
- 목표 2: 앞 k개 페이로드 패킷이 도달한 플로우 하나의 [특징 벡터 생성 + 단건 predict(스레드 설정 n_jobs=1)]. 패킷 도달 대기와 pcap 파싱은 제외하고 따로 적는다. 도달 플로우가 1,000개 미만이라 3개 시료의 전수를 썼다(k=5 n=309, k=10 n=277). 판정 = p95 ≤ 10ms, 최댓값·10ms 초과 건수 기록. 행별 측정(플로우 식별자·단건 ms·도달 대기 초)은 `DATA_DIR/perf_runs/`에 두고 Git에는 SHA만 기록했다.

## 후속 측정: RF 단건 지연 원인 분해와 경량화 (안건 11, Colab CPU 2026.07)
#42 주 수치(모델 구성 고정)와 분리한 진단이다. 코드 `src/track_b/perf_followup.py`, 결과 `outputs/results/track_b_perf_followup_2026-11-05_colab/`(Colab, 논리 CPU 2, 소스 묶음 `e3d539b`)와 Windows 참고 `..._win_v1`. 변형(사전 고정): RF 트리 100·50·25 × 입력 DataFrame·numpy + LightGBM 기준, k=5·10, 같은 플로우(k=5 n=309, k=10 n=277), 변형마다 워밍업·3패스·패스마다 변형 순서 순환. 통과 기준: 3패스 모두 전체 지연 p95 ≤ 10ms(전체는 직접 잰 값이며 벡터·추론 p95를 더하지 않는다).

- 단계별(패스별 p95의 중앙값, ms, k=5 / k=10): 벡터 생성은 DataFrame 0.8~1.1, numpy 0.02~0.03으로 작고, 지연의 대부분은 predict이다(RF 100 DataFrame predict 10.1 / 15.2, LightGBM 2.6 / 1.6). 즉 RF 100그루 predict 자체가 이 환경에서 10ms 안팎이다.
- 트리 수를 줄이면 전체 지연이 줄었다(RF 100→25: 약 1/2~1/5). 입력을 numpy로 바꾸면 벡터 생성 약 1ms가 사라지지만 predict는 변형에 따라 오히려 길어진 경우도 있어(RF 100 k5) 효과가 일관되지 않다. Colab에서 실행마다 변동이 커서(같은 변형의 패스 간 차이) 단일 숫자보다 3패스 판정을 본다.
- **예측 불일치**: 같은 트리 수의 DataFrame·numpy 모델 사이 6개 조합 모두 33,199행 중 0건.
- **C1 정확도(같은 분포, 쉬운 구분, 변형 선택에 쓰지 않음)**: 2021 04-11 학습, 04-16 시험. 조건 A(정상 + .242.104 공격) 혼동 건수·macro-F1은 RF 100/50/25가 k=5에서 TP 1,528·FN 5·FP 0(macro-F1 0.9991), k=10에서 TP 1,530·FN 3·FP 1(0.9993)로 **세 트리 수가 같았다**. 조건 B(정상 + 새 피해자 .88.81 공격)는 모두 recall 0(TP 0, FN 3,951; macro-F1 0.4667). 트리 수 축소는 이 시험(시드 1개)에서 정확도 변화가 없었고, 새 피해자 일반화는 트리 수와 무관하게 실패한다.
- 해석 한정: 이 결과는 Colab(논리 CPU 2) 한 번의 실행이다. 트리 수를 줄이는 것이 경량화에 유효하다는 관측이며, 서비스 모델로 정하는 것은 정확도(다른 조건·시드)와 설명 가능성을 포함한 별도 합의가 필요하다. LightGBM k=5 이상치(#42의 76.58ms)는 이번 3패스에서 재현되지 않았다(3패스 전체 최댓값 5.31ms, 최대 p95 3.51ms). 일회성 지연으로 보이나 원인은 확인하지 않았다.

## 한계
- 시료가 3개 pcap의 앞부분 10MiB뿐이고 payload>0 플로우가 81~133개로 적다. 플로우가 많은 트래픽에서는 시간이 달라질 수 있다.
- 단건 시간은 DataFrame 생성을 포함한 파이썬 호출 지연이며 서비스 지연(대시보드·네트워크·직렬화)은 측정하지 않았다. 환경별 한 번의 실행이다.
- 단건 판정은 n_jobs=1(단일 스레드) 기준이고, 10MiB 일괄 판정은 n_jobs=1과 -1을 모두 측정했다. 병렬화나 경량화 개선은 하지 않았다. 10MiB 처리 목표는 두 환경에서 충족했고, 플로우 1건 10ms 목표는 Windows에서 모두 충족, Colab에서는 LightGBM만 충족하고 RF는 미달이다.
