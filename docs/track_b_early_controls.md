# 트랙 B 통제 실험 (첫 길이 가리기·순서 섞기·부호 제거)

[#22](track_b_early_eval.md)의 macro-F1 ≥0.998이 어디서 나오는지 새 데이터 없이 확인하는 진단이다. 설계는 10/31 Slack `[토론 안건 1]`에서 Codex와 합의했다. **조기 탐지 능력의 근거가 아니다.** 단일 공격(Bruteforce-XML) 데이터의 오프라인 결과다.

## 조건

| 항목 | 내용 |
|---|---|
| 변형 | `mask_first`(seq_0만 0, 열을 당기지 않음), `shuffle`(앞 k개 안 비영 값을 행 ID+모델 시드로 독립 순열, 0 패딩 위치 고정), `abs`(절댓값, 방향 부호 제거). 각각 단독 적용 |
| 적용 순서 | 원본 앞 k개를 **먼저 자른 뒤** 변형(k 이후 패킷 유입 방지). train·test에 같은 규칙 |
| 평가 | 04-12↔04-17 양방향, k=5·10, RF·LightGBM, 시드 0·1·2. 3×2×2×2×3 = **72회** |
| 기준선 | #22 저장 예측(`track_b_early_2026-10-31_v3`)을 predictions SHA-256·정답 라벨 확인 후 재사용. 같은 시험 행에서 비교 |
| reached/short | 변형 전 `payload_packets`로 정하고 변형이 만든 0으로 다시 세지 않음 |
| 코드 | `src/track_b/early_controls.py`, 테스트 `tests/test_track_b_early_controls.py` 7개 |

## 해석 (합의된 범위)

1. 첫 패킷 길이를 가려도 점수가 거의 유지된다. 첫 길이는 충분하지만 이 데이터에서 필수는 아니다
2. 순서를 섞어도 유지된다. **이 설정에서** 위치 정보의 추가 이득이 작다
3. 방향 부호 제거는 차이가 없다. 이 설정에서 부호의 추가 이득이 작다
4. 세 요소가 동시에 불필요하다는 뜻은 아니다. 그 질문이 남으면 조합 통제를 후속으로 본다
5. 결과는 "점수가 높은 이유가 정교한 순서·방향 패턴이 아니다"를 보여 주며, 공격 플로우가 12개 이하·앞 5개 패턴 6종이라는 **쉬운 분리** 해석을 강화한다. 조기 탐지 능력은 공격 플로우가 k보다 긴 추가 공격 데이터에서 따로 보아야 한다
6. A의 순서 섞기와는 절대 F1이 아니라 각 데이터 내부의 변형 전후 차이 방향만 나란히 놓는다. A는 13종·그룹 분할·최대 30개, B는 2종·시간 분할·k=5·10이라 같은 관측 예산 비교가 아니다. 일치 여부는 A Colab 최종 결과 후 판단한다

## 한계

- 짧은 흐름(short) 부분집합은 정상만 있어 macro-F1이 0.5로 고정된다(클래스 누락에 따른 하향 편향). support·recall로 읽는다
- 시드는 모델 시드이며 섞기 순열에도 같은 시드를 쓴다. 시험 행이 같아 표준편차는 독립 재표집 구간이 아니다
- Windows 로컬 예비 결과이며 Colab 최종 실행은 없다
- 같은 코드·입력으로 다시 돌린 수치가 첫 실행(코드 커밋 전, dirty)과 같아 결정적임을 확인했다. 재현: 결과 폴더의 `metadata.json`에 flows·기준선·예측 SHA-256, 코드 SHA-256, Git 커밋을 기록한다
