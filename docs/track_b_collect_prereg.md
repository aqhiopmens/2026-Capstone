# B: 통제 수집 사전 고정 (안건 12, 수집 전 확정 문서) — 개정 3 (합의 전 초안)

Codex 18:25·18:43·20:22 의견, Opus 검토(시뮬레이션 추정 포함), Astra 판단(강민 전달)을 반영한 **합의 전 초안**이며 최종 확정이 아니다. 이 문서의 값은 모델 점수를 보기 전에 고정하고, 파일럿·본 수집 결과로 바꾸지 않는다(바꾸면 문서 끝 표에 사유와 날짜를 남기고 변경 전 결과도 보고한다). 결과는 실험실 통제 PoC이며 일반화 근거로 쓰지 않는다. 서버 3개는 노트북 1대의 포트 3개이고 인증서·TLS 구성만 다르므로 "서버 구성"으로만 쓴다(LOSO = 서버 구성 빼기).

## 1. 요청 구성·구현 교란 통제

목표: 정상/공격이 구현(requests/curl), 연결 재사용, 첫 요청, 응답 성공/실패 비율로 구분되지 않게 한다. loopback 관측은 연결당 요청 수가 requests 정상 4.29, 공격 6.0, curl 1.0이었고, 초안의 정상 첫 요청 `GET /`은 공격과 길이가 달라 k=10에서 요청 1개 길이만으로 구분되는 지름길이었다(Opus 지적).

| 항목 | 고정값 |
|---|---|
| 단위 정의 | **에피소드 요청 수**(러너가 한 에피소드에서 보낸 HTTP 요청 수)와 **TCP 연결당 요청 수**를 따로 기록한다. 이 설계에서는 에피소드 하나 = TCP 연결 하나(구현 무관, curl은 `--next`)이므로 둘이 같아야 하고, `conns_in_episode≠1`이면 그 연결을 제외·보고하며 러너가 쿼터를 채울 때까지 다시 수행한다 |
| 연결당 요청 수 m | 정상·공격·requests·curl 모두 같은 분포: m ∈ {1..6}, 라운드(칸당 10연결)당 다중집합 {1,1,2,2,3,3,4,4,5,6}을 섞어 쓴다(확률 추출 아님) |
| 첫 요청 | **`GET /`은 쓰지 않는다.** 두 클래스 모두 m≥2일 때 첫 요청 `GET /login` 50% / `POST` 50%. 이 비율은 서버 × 구현 × 시간 블록(라운드) × 클래스 안에서 맞추고, m·암호 길이와의 결합 분포도 블록 쿼터로 맞춘다(주변 비율만 같고 조합이 갈리는 것을 막음) |
| 정상 구성 | 오타 실패 0~3회 뒤 성공 로그인을 **마지막 요청**에 둔다. 정상 중 **라운드 칸당 정확히 2/10(20%)은 성공 없이 끝나는 실패 전용 에피소드**(m≥2). **m=1은 정상·공격 모두 첫 요청이 곧 유일한 요청**: `GET /login` 50% / `POST` 50%(m≥2의 첫 요청과 같은 비율, 블록 쿼터). **m=1의 첫 요청이 `GET /login`이면 로그인 시도가 없는 단일 페이지 요청**이라 정상·공격이 같은 요청이다(구별 불가 에피소드 — 정상·공격 라벨은 유지하되 "로그인 시도 없음" 부분집합으로 따로 세어 보고하고 이 행의 분류 불가를 한계로 적는다). m=1의 POST는 정상이면 성공 로그인, 공격이면 실패 로그인으로 고정한다. **"성공"은 로그인 POST의 인증 성공(서버 응답 200 + welcome)으로 정의**하며 GET의 HTTP 200은 성공으로 세지 않는다. 에피소드 유형별 인증 결과 배정표(m=1 GET/POST, m≥2 첫 요청 종류, 정상 성공 마지막/실패 전용, 공격 전부 실패)를 라운드 쿼터와 함께 코드에 하드코딩하고 파일럿에서 칸별 실제 개수로 검증한다. 정상 약 80%는 마지막에 성공하고 공격은 전부 실패로 끝나는 **응답 단서가 주 지표에 남는다**(제거되지 않음). 그래서 주 지표는 "통제된 로그인 시나리오 성능"으로, **실패 전용 정상 대 공격 부분집합 결과는 따로** 보고하고 둘을 섞어 해석하지 않는다 |
| 공격 구성 | POST 로그인 실패(암호 목록)를 기본으로 하되 첫 요청은 위 규칙을 따른다 |
| 정상 단순 방문 | 주 평가에서 뺀다. 필요하면 정상 칸에 라운드당 2개를 **별도 참고 부분집합**(`subset=browse`)으로 추가 수집하고, 학습·시험 주 지표에 넣지 않고 따로 보고한다. 주 평가의 해석은 "로그인 시나리오 안의 통제 구분"으로 한정하고 정상 대표성이 확보됐다고 읽지 않는다 |
| 본문·암호 | 로그인 본문 `u=admin&p=<암호>`의 암호 길이는 클래스 무관 6~14 균등. **정답 암호는 10자**로 바꾼다(기존 15자는 범위 밖이라 성공 POST가 길이로 식별됨) |
| 쿠키 | requests의 자동 쿠키 재전송(`Cookie: sid=1`, +13바이트)이 정상에만 생기는 비대칭을 막기 위해 쿠키 저장을 끈다(서버가 Set-Cookie를 보내도 클라이언트가 보관·재전송하지 않음). 성공을 마지막에 두는 규칙도 유지 |
| 간격 | **구현 안에서 클래스 간 동일**. requests: 요청 사이 U(0.02, 0.2)초(정상·공격 동일). curl `--next`는 요청 사이 지연을 넣을 수 없으므로 두 클래스 모두 연속 전송. 에피소드 사이 간격은 모든 칸 U(0.1, 0.5)초 |
| 연결 검증(파일럿) | curl·requests 모두 실제로 에피소드 1개 = TCP 연결 1개인지 pcap으로 확인한다(`conns_in_episode`). 재연결·분할이 생기면 그 에피소드를 제외하고 **재수행 기록**(제외 수, 재수행 수, 사유)을 칸별로 남긴다 |
| 승인 기준(파일럿) | 구현별로 정상 대 공격의 연결당 요청 수 평균 차이 ≤0.25(블록 쿼터라 구성상 0이어야 함), 첫 요청 종류·m·암호 길이 결합 분포가 칸마다 같음, 간격 중앙값 차이 ≤10% |
| 보고 | 구현×클래스별 연결 수·요청 수·성공/실패·평균 요청 수(`match` 보고서, 구현됨), 실패 로그인 부분집합(정상 실패 전용 대 공격)의 recall·FP, **서버×구현별 "앞 k개 안에 첫 요청이 들어온 비율"과 seq_0..5 분포**, S3 서버 비행의 세그먼트 수, 파일럿에서 `payload>1448` 패킷 유무(RSC. 있으면 클라이언트 NIC RSC를 끄고 다시 측정) |

통제가 맞지 않은 차이를 변수로 기록하는 것만으로 제거됐다고 해석하지 않는다. 성공 응답·쿠키·탐색 순서가 남는 단서는 실패 전용 정상 대 공격에서 따로 본다.

## 2. 수집 길이·시간 블록

계산: 서버당 15~20분에 앞 70%/뒤 30%이면 뒤 30%는 270~360초라 600초 간격을 두면 시험이 비게 된다. 그래서 서버를 번갈아 도는 두 단계로 한다.

- 한 라운드 = 4칸(정상·공격 × requests·curl) 각 10연결(정상 칸에는 별도 참고 2연결을 더 둘 수 있음), 라운드 안 순서는 시드 고정으로 섞는다. 모든 시간 블록에서 4칸이 같은 수다.
- 학습 단계: 서버당 30라운드(칸당 300). 시험 단계: 서버당 10라운드(칸당 100). 서버당 학습 1,200+시험 400, 3서버 4,800연결(주 평가).
- 순서: S1 학습 → S2 학습 → S3 학습 → S1 시험 → S2 시험 → S3 시험. **오케스트레이터가 각 서버의 시험 직전에 그 서버 학습·지원의 실제 마지막 연결 종료 시각 + 660초까지 자동 대기**한다(여유 60초). 시험 첫 연결 시각 − 학습·지원 마지막 종료 ≥600초를 로그로 검사해 보고하고, 미달 행은 시험에서 제외하며 개수를 적는다.
- 쿼터를 채우지 못하면(재수행 포함) 지속 시간을 늘리고 수량 기준을 낮추지 않는다. 예상 시간: 연결당 0.3~0.8초 + 에피소드 간격 → 4,800연결 약 24~108분(Opus 추정, 파일럿에서 실측).
- 파일럿은 **LAN에서** 수집·매칭 점검용으로만 쓰고 본 평가 학습·시험에 재사용하지 않는다(loopback은 Nagle·세그먼트 분할·티켓 경쟁이 재현되지 않음). 본 수집은 새 로그·새 pcap으로 한다.

## 3. 매칭·시계·epoch 기준

- 라벨은 러너 로그의 `(client_ip, client_port, server_ip, server_port)`와 시작 시각에서만 가져온다. IP·서버로 라벨을 정하지 않는다.
- **독립 기준**: 서버가 연결 수락마다 `(client_ip, client_port, server_port, 서버 벽시계 시각)`을 로그에 남긴다(구현 예정). 캡처도 서버 노트북에서 하므로 pcap 시각과 서버 로그가 같은 시계다. **기준 사건을 고정**한다: pcap은 SYN 시각(없으면 첫 payload 패킷), 서버 로그는 accept 시각이며, accept와 SYN/첫 payload는 다른 사건이라 이 지연을 시계 오차로 해석하지 않고 pcap↔서버 로그 지연으로 따로 보고한다. 러너↔서버 시계 offset은 **추정 offset과 보정 후 잔차를 나눠 기록**하고(MAD만으로는 고정 시계 편차를 검출하지 못함), 포트 재사용 epoch와 단조/벽시계 대응을 별도로 감사한다. 모두 필터 전 전체 후보에서 측정하며 ±1초 매칭 뒤의 잔차 분포(잘린 분포)는 정확도 검증으로 쓰지 않는다.
- 허용 오차 1.0초, 같은 4-튜플 후보가 둘 이상이면 **모호**(임의로 가까운 쪽을 고르지 않고 제외). 4-튜플 재사용·재접속은 연결 epoch(SYN) 단위로 분리하고, SYN 없는 발췌의 한계는 유지한다. 같은 4-튜플 다른 플로우와의 시간 범위 겹침 감사 결과를 남긴다.
- offset 추정: **서버 단계(학습/시험)별로 하나**, 서버 로그와 단일 후보로 매칭된 연결 전체의 중앙값을 쓰고 단계 안 구간별(라운드별) 편차도 보고한다. 같은 4-튜플 후보가 둘 이상이면 모호로 제외(임의 최근접 선택 금지). **어느 칸이든 (미매칭+모호) >2%이면 그 서버 단계의 해당 결과를 "손실 편향 위험"으로 표기하고 자동 폐기하지 않으며, 재수행 여부는 김강민이 정한다**(파일럿에서 초과하면 러너/캡처를 고쳐 파일럿을 다시 한다).
- 보고: 필터 전 후보 잔차, 모호·미매칭·epoch 사유를 **구현×클래스(칸)별**로 낸다. 승인: 서버 시계 offset 추정의 MAD ≤0.2초, 각 칸의 (미매칭+모호) ≤2%. **전체 평균만으로 통과시키지 않고 칸마다 적용**한다. 제외로 생긴 손실 편향(칸·서버·시간별 손실 비율)을 보고한다.
- 본 수집은 커밋 해시로 코드·설정을 고정하고 `git_dirty_src_tests=false`에서 실행한다.

## 4. 평가 설계

- 입력: seq, seq_mask3(seq_0~2 가림). **k=5, 10이 주 평가, k=15는 보조**(사전 등록, 전체 조건 보고). 모델: RF·LightGBM(기존 고정 설정), 시드 3(모델 난수만 바꾸므로 반복 표본으로 세지 않음).
- **(a) 서버 구성 단위 LOSO**: 학습 = 두 서버의 학습 단계, 시험 = 뺀 서버의 학습·시험 단계 전체. 3회, 폴드별 값을 그대로 보고.
- **(b) 서버 안 시간 분할**: 학습 = 같은 서버의 학습 단계, 시험 = 시험 단계(간격 ≥600초).
- 설정·스케일러·문턱·특징 선택은 각 fold의 학습·지원 데이터에서만 정한다. 시험 행은 어디에도 접근하지 못한다.
- 지표: macro-F1, 클래스별 recall, **정상 FP 건수와 분모**, 칸(구현×클래스)별·실패 로그인 부분집합별 값. 정상 분모 600(3서버 합), 폴드별 200 → FP 0건일 때 Wilson 95% 상한 0.636%, 폴드별 1.885%(Codex 직접 계산). 반복 연결 상관과 구성 3개 한계 때문에 미래 환경 FPR 보장으로 쓰지 않는다.

### 4.0 k=5 사전 가설과 진단 (Astra·Codex 반영)
> k=5는 우연 기준에 가까운 성능을 보일 것으로 예상한다(앞 5개 패킷은 TLS 1.3 핸드셰이크와 세션 티켓 위주라 행동 신호가 거의 없다는 추정). 관측 성능과 관계없이 모든 결과를 보고하며, 지름길 여부는 사전에 정한 진단으로 평가한다.

- 예상보다 높은 점수를 결과 제외·지름길 판정의 기준으로 쓰지 않는다. Opus의 이론 상한(S1·S2 k=10 약 0.80, S3 k=10 약 0.65)은 명시한 생성 모형의 시뮬레이션 추정치이며 판정 기준이 아니다. '우연 수준'도 accuracy/균형정확도/macro-F1과 예측 규칙에 따라 달라 약 0.5로 뭉뚱그리지 않는다.
- 사전 진단(점수를 보기 전 정의): ① 앞 k개 안에 첫 요청이 들어오는 위치·비율(서버×구현별), ② 실패 전용 정상 대 공격 부분집합 값, ③ 구현·서버 구성별 값, ④ 특징 중요도·선택 칸 목록.

### 4.1 교락 학습 대 혼합 학습
- 고정 시험 집합 T = 세 서버 시험 단계의 정상·공격 전부(학습에 쓴 행 제외).
- 혼합 학습: 세 서버 학습 단계의 정상·공격 모두. 교락 학습(HIKARI 구조 재현): 공격은 S1 학습 단계만, 정상은 S2·S3 학습 단계만. **서버와 시간이 함께 교락**된다(공격이 가장 이른 시간대에서만 나옴, HIKARI와 같은 구조).
- 학습 표본 수·클래스 비율을 같게: 클래스별 표본 수를 두 설계 가능 수의 최솟값(공격 600)으로 고정하고, 혼합 설계는 서버×구현으로 층화해 셀당 100행을 뽑는다(시드 고정). 같은 T에서만 비교한다.

### 4.2 소수 라벨 2×2
- 요인 A = **지원 라벨을 학습 행에 추가하는가**(아니오/예). 요인 B = **지원 라벨을 특징 선택에 쓰는가**(아니오/예). 네 칸: 무지원 / 라벨 추가만 / 특징 선택만 / 둘 다. 특징 선택만도 지원 라벨을 소비하는 적응이며 무지원과 다르다.
- **지원 = 보류 서버의 학습 단계 처음 N개**를 클래스(정상·공격)별로 뽑고(Codex·Opus 합의 방향), 시험은 그 서버의 시험 단계 전체다. **N = 클래스당 6/10 = 총 12/20, 구현당 3/5**(구현별 층화). 지원 후보·에피소드와 시험은 겹치지 않으며, 지원 마지막 연결/에피소드 종료 이후 시험 시작 간격(≥600초)을 감사한다.
- **무지원 원 모델은 보류 서버 전체를 학습에서 제외**하고 지원 라벨을 받지 않는다. 지원은 라벨을 쓰는 적응 조건(A=예 또는 B=예)에만 전달한다. 모든 조건에서 같은 지원 후보·예산·미래 시험 행을 쓴다. **이번 평가의 지원은 "러너 정답 기반 oracle 층화 지원"으로 확정한다**: 러너 로그의 정답으로 보류 서버 학습 단계에서 클래스·구현별 처음 3/5개를 골라 주며, 그 지원을 찾기 위해 사람이 추가로 읽는 라벨 조회량은 예산에 넣지 않는다. 따라서 "실제로 N개를 읽어 찾은 경우"와 다른 조건이며 그 해석을 하지 않는다(필요하면 별도 조건으로 후속).
- **특징 선택 규칙(탐색용 고정값, 시험 점수로 바꾸지 않음)**: 유효 후보 칸 = 학습 행에서 분산이 0이 아닌 seq 앞 k칸. 각 칸마다 **원 서버(두 학습 서버) 학습 행으로 깊이 1 스텀프**를 학습하고 **지원 행의 균형 정확도**로 순위를 매겨 **상위 r칸 유지**(k=5: r=2, k=10: r=4, k=15: r=6). 동률은 원 서버 학습 정확도 → 열 번호 순. 선택된 칸 목록을 폴드·N별로 보고한다. r과 N은 최적이라는 근거가 없는 실행 예산 기반 값이며, 12/20 라벨에서 순위 변동과 다중비교 불안정이 남는다.
- 후보 정의는 **마스킹 적용 후**의 열이다. 후보 수 < r이면 후보를 전부 유지한다(선택이 개입하지 않음). 동률 규칙은 위와 같다.
- **k=5 + 마스킹**은 후보가 seq_3·seq_4 두 칸뿐이고 r=2라 선택이 실제로 개입하지 않으므로 요인 B는 "효과 없음/식별 불가"로 보고한다.
- 해석 한정: B019식 지름길 제거에 대응시킨 시도이며 재현이 아니다.

## 5. 한계
실험실 트래픽은 단순하고 도구 2종·서버 구성 3개(노트북 1대 포트 3개)·공격 한 유형·같은 앱·한 LAN이다. LOSO는 3회뿐이다. 클라이언트 OS가 하나라 기기·OS 변화는 시험하지 못한다. requests/curl이 TLS 구현의 서명이 될 수 있어 두 구현을 정상·공격 모두에 쓰지만 구현 효과가 완전히 제거되지는 않는다. S3(RSA-4096 2단 체인)는 서버 첫 비행이 여러 세그먼트로 갈릴 수 있고(추정, 파일럿 확인), LAN/오프로드로 세그먼트 구성이 loopback과 달라질 수 있다. 서버 시계와 러너 시계가 달라 시각 매칭에 의존한다. 정상 대표성은 확보되지 않았다.
