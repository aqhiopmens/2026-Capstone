# B: 통제 수집 사전 고정 (안건 12, 수집 전 확정 문서) — 개정 5b (합의 전 초안)

Codex 18:25·18:43·20:22 의견, Opus 검토(시뮬레이션 추정 포함), Astra 판단(강민 전달)을 반영한 **합의 전 초안**이며 최종 확정이 아니다. 이 문서의 값은 모델 점수를 보기 전에 고정하고, 파일럿·본 수집 결과로 바꾸지 않는다(바꾸면 문서 끝 표에 사유와 날짜를 남기고 변경 전 결과도 보고한다). 결과는 실험실 통제 PoC이며 일반화 근거로 쓰지 않는다. 서버 3개는 노트북 1대의 포트 3개이고 인증서·TLS 구성만 다르므로 "서버 구성"으로만 쓴다(LOSO = 서버 구성 빼기).

## 1. 요청 구성·구현 교란 통제

목표: 요청 구성의 **비의도적 차이**(구현, 연결 재사용, 첫 요청, 요청 수, 암호 길이, 간격)를 통제해 정상/공격이 그 차이로 구분되지 않게 한다. **인증 결과(성공/실패)에 따른 응답 단서는 통제되지 않고 잔존 한계로 보고한다.** loopback 관측은 연결당 요청 수가 requests 정상 4.29, 공격 6.0, curl 1.0이었고, 초안의 정상 첫 요청 `GET /`은 공격과 길이가 달라 k=10에서 요청 1개 길이만으로 구분되는 지름길이었다(Opus 지적).

| 항목 | 고정값 |
|---|---|
| 단위 정의 | **에피소드 요청 수**(러너가 한 에피소드에서 보낸 HTTP 요청 수)와 **TCP 연결당 요청 수**를 따로 기록한다. 이 설계에서는 에피소드 하나 = TCP 연결 하나(구현 무관, curl은 `--next`)이므로 둘이 같아야 하고, `conns_in_episode≠1`이면 그 연결을 제외·보고하며 러너가 쿼터를 채울 때까지 다시 수행한다 |
| 연결당 요청 수 m | 정상·공격·requests·curl 모두 같은 분포: m ∈ {1..6}, 라운드(칸당 10연결)당 다중집합 {1,1,2,2,3,3,4,4,5,6}을 섞어 쓴다(확률 추출 아님) |
| 첫 요청 | **`GET /`은 쓰지 않는다.** 두 클래스 모두 m≥2일 때 첫 요청 `GET /login` 50% / `POST` 50%. 이 비율은 서버 × 구현 × 시간 블록(라운드) × 클래스 안에서 맞추고, m·암호 길이와의 결합 분포도 블록 쿼터로 맞춘다(주변 비율만 같고 조합이 갈리는 것을 막음) |
| 정상 구성(라운드 칸당 10연결) | **인증 성공 7 / 실패 전용 2 / 로그인 시도 없음 1**(= 70% / 20% / 10%). 인증 성공 에피소드는 성공 로그인 POST를 **마지막 요청**에 둔다. 실패 전용은 성공 없이 끝나는 에피소드(로그인 9칸 중 회전 배정, `(POST,1)` 포함), 로그인 시도 없음은 m=1 `GET /login` 1개. **실패 전용 2개는 특정 (첫 요청, m) 칸에 고정하지 않는다**(고정하면 "그 칸에서 실패로 끝남 = 공격"이라는 규칙이 배정표만으로 성립해, 파일럿에서 RF가 이를 외워 오탐 0 공격 비율이 k=20 42.5%·k=30 61.7%가 됐다). 라운드마다 `GET /login` 1개 칸을 뺀 로그인 9칸 중 2칸을 구현별로 돌려 배정하며(`failonly_cells`), 구현당 9라운드에 칸마다 정확히 2번, 그 밖의 라운드 수에서도 칸별 횟수 차이 ≤1이다. **실패 POST·GET·성공 POST의 순서와 개수는 총 요청 수 m과 일치하는 에피소드 유형별 배정표로 코드에 고정**한다(m=5·6에서 남는 요청도 배정표가 정한다) |
| 공격 구성 | POST 로그인 실패(암호 목록)를 기본으로 하되 첫 요청은 위 규칙을 따른다. **m=1도 정상·공격 각각 `GET /login` 50%·`POST` 50%로 배정한다. 인증 성공은 로그인 POST의 200+welcome으로 정의하며, GET의 HTTP 200은 인증 성공으로 세지 않는다.** m=1 `GET /login`은 로그인 시도 없음(정상 쪽 쿼터 1/10), m=1 `POST`는 정상이면 배정에 따라 성공 또는 실패(실패 전용 회전에 포함)·공격이면 실패 |
| 정상 단순 방문 | 주 평가에서 뺀다. 필요하면 정상 칸에 라운드당 2개를 **별도 참고 부분집합**(`subset=browse`)으로 추가 수집하고, 학습·시험 주 지표에 넣지 않고 따로 보고한다. 주 평가의 해석은 "로그인 시나리오 안의 통제 구분"으로 한정하고 정상 대표성이 확보됐다고 읽지 않는다 |
| 본문·암호 | 로그인 본문 `u=admin&p=<암호>`. 정답(성공) 암호는 **10자**(기존 15자는 통제 범위를 벗어나 성공 POST가 길이로 식별됨). **성공 POST의 10자 암호를 포함해, 에피소드 유형·m·요청 위치별 암호 길이 배정표를 클래스 간 동일하게 고정**하고, 공격에는 같은 길이의 오답을 쓴다. 정상 오타 실패 암호의 길이도 같은 배정표를 따른다 |
| 쿠키 | requests의 자동 쿠키 재전송(`Cookie: sid=1`, +13바이트)이 정상에만 생기는 비대칭을 막기 위해 쿠키 저장을 끈다(서버가 Set-Cookie를 보내도 클라이언트가 보관·재전송하지 않음). 성공을 마지막에 두는 규칙도 유지 |
| 간격 | **구현 안에서 클래스 간 동일**. requests: 요청 사이 U(0.02, 0.2)초(정상·공격 동일). curl `--next`는 요청 사이 지연을 넣을 수 없으므로 두 클래스 모두 연속 전송. 에피소드 사이 간격은 모든 칸 U(0.1, 0.5)초 |
| 연결 검증(파일럿) | curl·requests 모두 실제로 에피소드 1개 = TCP 연결 1개인지 pcap으로 확인한다(`conns_in_episode`). 재연결·분할이 생기면 그 에피소드를 제외하고 **재수행 기록**(제외 수, 재수행 수, 사유)을 칸별로 남긴다 |
| 승인 기준(파일럿) | 구현별로 정상 대 공격의 연결당 요청 수 평균 차이 ≤0.25(블록 쿼터라 구성상 0이어야 함), 첫 요청 종류·m·암호 길이 결합 분포가 칸마다 같음, 간격 분포는 구현 안에서 두 클래스가 같은 난수 분포라 구성상 같으며, 중앙값 차이는 합격 판정이 아니라 **보고**만 한다(파일럿 requests `t_k10` 중앙값 정상 0.068초·공격 0.077초, 표본이 작아 무작위 차이로 봄). 이는 **파일럿 결과에 따른 기준 변경**이며, `t_k10`은 요청 간격만이 아니라 TLS·응답·네트워크 지연이 섞인 관측시간이므로 **정상·공격별 실제 요청 간격 분포와 `t_k` 분포를 따로** 보고한다 |
| 보고 | 구현×클래스별 연결 수·요청 수·인증 성공/실패·평균 요청 수(`match` 보고서, 구현됨), 실패 로그인 부분집합(정상 실패 전용 대 공격)의 recall·FP, **서버×구현별 "앞 k개 안에 첫 요청이 들어온 비율"과 seq_0..5 분포**(loopback 관측의 "curl은 k=5에 요청이 들어오지 않는다"는 **LAN 파일럿에서 기각**됐다: curl S1·S2 55~60%, requests 99%, S3는 서버 첫 비행이 3세그먼트라 둘 다 0%), **서버×구현×k별 "앞 k개 안에 인증 성공 응답이 보이는 정상 행 비율"(성공 응답 노출률, 4.0b의 상한 계산 입력)**, S3 서버 비행의 세그먼트 수, pcap 손실(`skipped`)과 `payload>1460`(MSS) 개수. 캡처는 서버 노트북에서 하므로 문제가 되는 것은 **서버 NIC의 LSO(송신)·RSC(수신)**이다(유선이면 둘 다 끄고 다시 측정, Npcap은 LSO 패킷의 IP 길이를 0으로 찍어 추출기가 조용히 버릴 수 있다). 서버 소켓은 TCP_NODELAY로 둔다 |

통제가 맞지 않은 차이를 변수로 기록하는 것만으로 제거됐다고 해석하지 않는다. 성공 응답·쿠키·탐색 순서가 남는 단서는 실패 전용 정상 대 공격에서 따로 본다.

**잔존 단서(Opus 계산 추정, 파일럿에서 확인)**: 인증 결과에 따른 응답 길이가 남는다. 성공 응답(200 + Set-Cookie 헤더, 본문 welcome)은 실패 응답(401, denied)과 레코드 길이가 달라서, k=10 안에 성공 응답이 들어온 정상 행이 curl에서 약 30%, requests에서 약 10%(loopback, **추정치이며 정상의 30%가 구분된다는 뜻이 아님**)이다. k=5에서는 0이다. 응답 길이를 맞추지 않고 잔존 한계로 보고하며(Codex 합의), 실패 전용 정상 대 공격 부분집합이 이를 가려내는 진단이다. 브라우즈 참고 부분집합(`subset=browse`)은 정상에만 있고 `GET /`을 써 길이가 다르므로 평가 코드는 `subset=="main"`으로 거른다. 공격 칸의 10%(m=1 `GET /login`)는 정상의 "로그인 시도 없음"과 완전히 같은 트래픽이다.

**파일럿 1 관측(Opus 진단, 정상 행, 표본 작음·탐색)**: 성공 응답(헤더 -152, 본문 -29)과 실패 응답(-143, -28)이 결정적으로 갈리고 공격에는 -152가 없다. 앞 k개 안에 -152가 들어온 정상 행 비율은 k=5에서 0, k=10에서 curl S1·S2 약 0.3·requests와 S3 약 0.1, k=15에서 0.3~0.4, k=30에서 약 0.7이다. 요청 쪽 양수 길이 분포는 두 클래스가 같았다. 따라서 실패 전용 칸 고정을 푼 뒤 남는 클래스 신호는 사실상 "인증 결과 응답이 앞 k개 안에 보이는가" 하나다(단일 연결 안의 공격 행동 신호는 설계상 제거하려 했음). 다만 `-152`는 길이만으로 정한 **후보 판정**이며 세그먼트 분할·합쳐짐·미확인 연결은 따로 표기하고, 실패 전용 회전은 고정 칸 단서를 완화한 것이지 모든 요청 구성 단서의 제거를 입증한 것이 아니다(Codex).

## 2. 수집 길이·시간 블록

계산: 서버당 15~20분에 앞 70%/뒤 30%이면 뒤 30%는 270~360초라 600초 간격을 두면 시험이 비게 된다. 그래서 서버를 번갈아 도는 두 단계로 한다.

- 한 라운드 = 4칸(정상·공격 × requests·curl) 각 10연결(정상 칸에는 별도 참고 2연결을 더 둘 수 있음), 라운드 안 순서는 시드 고정으로 섞는다. 모든 시간 블록에서 4칸이 같은 수다.
- 학습 단계: 서버당 30라운드(칸당 300). 시험 단계: 서버당 10라운드(칸당 100). 서버당 학습 1,200+시험 400, 3서버 4,800연결(주 평가).
- 순서: S1 학습 → S2 학습 → S3 학습 → S1 시험 → S2 시험 → S3 시험. **오케스트레이터가 각 서버의 시험 직전에 그 서버의 마지막 학습·지원 에피소드에 속한 모든 연결의 종료 시각 + 660초까지 자동 대기**한다(여유 60초). 시험 첫 연결 시각 − 학습·지원 마지막 종료 ≥600초를 로그로 검사해 보고하고, 미달 행은 시험에서 제외하며 개수를 적는다.
- 쿼터를 채우지 못하면(재수행 포함) 지속 시간을 늘리고 수량 기준을 낮추지 않는다. 예상 시간: 연결당 0.3~0.8초 + 에피소드 간격 → 4,800연결 약 24~108분(Opus 추정, 파일럿에서 실측).
- 파일럿은 **LAN에서** 수집·매칭 점검용으로만 쓰고 본 평가 학습·시험에 재사용하지 않는다(loopback은 Nagle·세그먼트 분할·티켓 경쟁이 재현되지 않음). 본 수집은 새 로그·새 pcap으로 한다.
- 파일럿 환경 점검(집): 서버 노트북 방화벽에서 python.exe 인바운드 8443~8445 허용·네트워크 프로필 Private, `--bind 0.0.0.0`과 `--host`는 IPv4 주소 그대로, 서버 NIC LSO·RSC 끄기(유선), 두 PC 절전·Wi-Fi 절전·화면 꺼짐 끄기, 실행 직전 두 PC `w32tm /resync`, 데스크톱은 Windows 11(Schannel TLS 1.3)·Python·requests·urllib3 버전 기록(`run`이 `.meta.json`에 자동 기록: 커밋·dirty·시드·curl·OpenSSL 등), 저장소 루트에서 실행. 일정용 난수와 암호·간격용 난수를 분리해 재시도가 있어도 라운드 구성은 같다.

## 3. 매칭·시계·epoch 기준

- 라벨은 러너 로그의 `(client_ip, client_port, server_ip, server_port)`와 시작 시각에서만 가져온다. IP·서버로 라벨을 정하지 않는다.
- **독립 기준**: 서버가 연결 수락마다 `(client_ip, client_port, server_port, 서버 벽시계 시각)`을 로그에 남긴다(구현 예정). 캡처도 서버 노트북에서 하므로 pcap 시각과 서버 로그가 같은 시계다. **기준 사건을 고정**한다: pcap은 SYN 시각(없으면 첫 payload 패킷), 서버 로그는 accept 시각이며, accept와 SYN/첫 payload는 다른 사건이라 이 지연을 시계 오차로 해석하지 않고 pcap↔서버 로그 지연으로 따로 보고한다. 러너↔서버 시계 offset은 **추정 offset과 보정 후 잔차를 나눠 기록**하고(MAD만으로는 고정 시계 편차를 검출하지 못함), 포트 재사용 epoch와 단조/벽시계 대응을 별도로 감사한다. 모두 필터 전 전체 후보에서 측정하며 ±1초 매칭 뒤의 잔차 분포(잘린 분포)는 정확도 검증으로 쓰지 않는다.
- 허용 오차 1.0초, 같은 4-튜플 후보가 둘 이상이면 **모호**(임의로 가까운 쪽을 고르지 않고 제외). 4-튜플 재사용·재접속은 연결 epoch(SYN) 단위로 분리하고, SYN 없는 발췌의 한계는 유지한다. 같은 4-튜플 다른 플로우와의 시간 범위 겹침 감사 결과를 남긴다.
- offset 추정: **서버 단계(학습/시험)별로 하나**. 시간 허용오차 필터 적용 전, 4-튜플·epoch로 유일하게 대응되는 runner–server 연결의 `서버 기준시각 − runner 기준시각` 중앙값을 단계별 정렬 offset으로 쓰고, 단계 안 구간별(라운드별) 편차도 보고한다. 서로 다른 사건의 지연을 포함하므로 순수 시계오차로 해석하지 않는다. **기준 연결이 부족하면 offset=0으로 대체하지 않고 파일럿을 불합격 처리**한다. 같은 4-튜플 후보가 둘 이상이면 모호로 제외(임의 최근접 선택 금지). **(미매칭+모호) ≤2%는 파일럿 합격 기준**이고, 본 수집에서 칸별로 초과한 결과는 폐기하지 않고 보존하며 "손실 편향 위험"으로 표기한다. 재수행 여부는 김강민이 **모델 점수를 확인하기 전에** 정한다. offset은 (단계, 서버)별로 따로 추정해 보고하고(전체 하나만 쓰지 않음, 실행 중 시계가 튀는 경우 대비) 구현별·라운드별 보정 후 잔차 중앙값도 남긴다(curl은 프로세스 시작 지연이 있어 구현별로 다르게 나온다). 서버가 실패한 TLS 핸드셰이크도 `hs_fail` 행으로 남긴다.
- 보고: 필터 전 후보 잔차, 모호·미매칭·epoch 사유를 **구현×클래스(칸)별**로 낸다. 승인: 서버 시계 offset 추정의 MAD ≤0.2초, 각 칸의 (미매칭+모호) ≤2%. **전체 평균만으로 통과시키지 않고 칸마다 적용**한다. 제외로 생긴 손실 편향(칸·서버·시간별 손실 비율)을 보고한다.
- 본 수집은 커밋 해시로 코드·설정을 고정하고 `git_dirty_src_tests=false`에서 실행한다.

## 4. 평가 설계

- 입력: seq, seq_mask3(seq_0~2 가림). **k=5, 10이 주 평가, k=15는 보조**(사전 등록, 전체 조건 보고). 모델: RF·LightGBM(기존 고정 설정), 시드 3(모델 난수만 바꾸므로 반복 표본으로 세지 않음).
- **(a) 서버 구성 단위 LOSO**: 학습 = 두 서버의 학습 단계, **시험 = 보류 서버의 시험 단계 전체로 고정**(정상 분모 폴드당 200, 3폴드 합 600). 3회, 폴드별 값을 그대로 보고. 무지원·적응 네 조건 모두 같은 미래 시험 행을 쓴다.
- **(b) 서버 안 시간 분할**: 학습 = 같은 서버의 학습 단계, 시험 = 시험 단계(간격 ≥600초).
- 설정·스케일러·문턱·특징 선택은 각 fold의 학습·지원 데이터에서만 정한다. 시험 행은 어디에도 접근하지 못한다.
- 지표: macro-F1, 클래스별 recall, **정상 FP 건수와 분모**, 칸(구현×클래스)별·실패 로그인 부분집합별 값. 정상 분모 600(3서버 합), 폴드별 200 → FP 0건일 때 Wilson 95% 상한 0.636%, 폴드별 1.885%(Codex 직접 계산). 반복 연결 상관과 구성 3개 한계 때문에 미래 환경 FPR 보장으로 쓰지 않는다.

### 4.0 k=5 사전 가설과 진단 (Astra·Codex 반영)
> k=5는 우연 기준에 가까운 성능을 보일 것으로 예상한다(앞 5개 패킷은 TLS 1.3 핸드셰이크와 세션 티켓 위주라 행동 신호가 거의 없다는 추정). 관측 성능과 관계없이 모든 결과를 보고하며, 지름길 여부는 사전에 정한 진단으로 평가한다.

- 예상보다 높은 점수를 결과 제외·지름길 판정의 기준으로 쓰지 않는다. Opus의 이론 상한(S1·S2 k=10 약 0.80, S3 k=10 약 0.65)은 명시한 생성 모형의 시뮬레이션 추정치이며 판정 기준이 아니다. '우연 수준'도 accuracy/균형정확도/macro-F1과 예측 규칙에 따라 달라 약 0.5로 뭉뚱그리지 않는다.
- 사전 진단(점수를 보기 전 정의): ① 앞 k개 안에 첫 요청이 들어오는 위치·비율(서버×구현별), ② 실패 전용 정상 대 공격 부분집합 값, ③ 구현·서버 구성별 값, ④ 특징 중요도·선택 칸 목록.

### 4.0a 조기 탐지 판정 기준 (Codex 권고, 수집·평가 전에 고정)
이번 통제 수집 한 번을 판단 기준으로 쓴다. 해석은 결과를 보기 전에 정한다.
- k=5·10·15에서 낮은 오탐으로 탐지되면: 확인한 조건에 한정해 조기 탐지 가능성을 보고한다.
- 뒤쪽 패킷에서만 구분되면: 필요한 관측량과 시간의 한계를 보고한다.
- 끝내 구분되지 않으면: 조기 탐지를 주 성과에서 내려놓고 실패 원인·일반화 한계·소량 라벨 적응을 성과로 정리한다.
"낮은 오탐"은 연결 단위 누적 FPR ≤1%를 **설계 목표**로 쓴다(보장된 상한이 아님). 폴드별 정상 200행에서는 FP 0건이어도 양측 95% Wilson 상한이 약 1.885%이므로 시험 결과로 "1% 이하를 보장했다"고 주장하지 않는다.


### 4.0b 이진 응답 단서 기준선과 해석 한정 (개정 5a, 점수를 보기 전에 계산)
- **가정**: 앞 k개 안에서 클래스를 가르는 단서가 "인증 성공 응답이 보인다"(공격에는 없음)라는 이진 변수 하나뿐이고, 노출되지 않은 정상과 공격의 나머지 prefix 분포가 같다. 이 가정 아래 최적 균형정확도는 0.5 + 0.5·p_k(p_k = 정상 중 노출 비율)다. **이는 전체 입력 모델의 상한이 아니라 이 이상화 조건의 기준선이다.**
- 같은 가정에서 FPR ≤ α이면 무작위화를 허용한 TPR ≤ min(1, α/(1−p_k))이다(p_k=0.7, α=0.01이면 약 3.3%). 따라서 "FPR 1% 이하에서 탐지가 0"이라고 일반적으로 단정하지 않는다. 본 수집의 시험 단계에서 서버×구현×k별 p_k와 이 기준선(균형정확도, α=1%에서의 TPR 한도)을 **모델 점수를 보기 전에** 계산해 결과 표와 함께 낸다. 가정이 깨지는지(나머지 분포 차이)는 관측 성능이 기준선을 넘는지로 본다.
- 관측 성능이 기준선을 넘으면 새 단서의 증거로 보지 않고 먼저 지름길 진단(4.0)으로 확인한다. `-152` 판정은 후보 규칙이므로 분할·합쳐짐·미확인 연결 수를 함께 낸다.
- 실패 전용 정상 대 공격은 응답 결과가 같게 설계된 부분집합이다. 우연 수준에 가까우면 **"이 진단에서 잔존 단서를 발견하지 못했다"**로, 높으면 아직 남은 단서가 있다는 뜻이다("제거가 입증됐다"고 쓰지 않는다). 이 부분집합을 주 진단으로 먼저 보고한다.
- 해석 한정: 이 수집에서 조기 탐지가 안 되는 결과가 나오면 연결 하나 안의 초기 패킷에 로그인 실패 행동 외 구분 신호가 없게 설계했기 때문일 수 있고, 일반 공격의 조기 탐지가 불가능하다는 뜻이 아니다. 탐지가 되어도 응답 결과 단서에 기댄 것일 수 있어 일반 공격 탐지 성능으로 읽지 않는다.
- 서버별 성공 응답 노출률을 LOSO 폴드 결과 옆에 함께 보고한다(S3는 서버 비행이 3세그먼트라 k=10 노출률이 낮을 수 있어 폴드 간 차이가 일반화가 아니라 인증서 체인 길이에서 올 수 있다). mask3을 써도 S3의 `seq_3`(-366)은 서버 식별로 남을 수 있다.

### 4.1 교락 학습 대 혼합 학습
- 고정 시험 집합 T = 세 서버 시험 단계의 정상·공격 전부(학습에 쓴 행 제외).
- 혼합 학습: 세 서버 학습 단계의 정상·공격 모두. 교락 학습(HIKARI 구조 재현): 공격은 S1 학습 단계만, 정상은 S2·S3 학습 단계만. **서버와 시간이 함께 교락**된다(공격이 가장 이른 시간대에서만 나옴, HIKARI와 같은 구조).
- 학습 표본 수·클래스 비율을 같게: **두 설계 모두 정상 600·공격 600행**. 혼합은 클래스별 서버×구현 6셀에 100행씩, 교락(HIKARI 구조)은 공격 S1의 구현별 300행·정상 S2/S3의 구현별 150행씩(시드 고정 추출). 같은 T에서만 비교한다.

### 4.2 소수 라벨 2×2
- 요인 A = **지원 라벨을 학습 행에 추가하는가**(아니오/예). 요인 B = **지원 라벨을 특징 선택에 쓰는가**(아니오/예). 네 칸: 무지원 / 라벨 추가만 / 특징 선택만 / 둘 다. 특징 선택만도 지원 라벨을 소비하는 적응이며 무지원과 다르다.
- **지원 = 보류 서버의 학습 단계 처음 N개**를 클래스(정상·공격)별로 뽑고(Codex·Opus 합의 방향), 시험은 그 서버의 시험 단계 전체다. **N = 클래스당 6/10 = 총 12/20, 구현당 3/5**(구현별 층화). 지원 후보·에피소드와 시험은 겹치지 않으며, 지원 마지막 연결/에피소드 종료 이후 시험 시작 간격(≥600초)을 감사한다.
- **무지원 원 모델은 보류 서버 전체를 학습에서 제외**하고 지원 라벨을 받지 않는다. 지원은 라벨을 쓰는 적응 조건(A=예 또는 B=예)에만 전달한다. 모든 조건에서 같은 지원 후보·예산·미래 시험 행을 쓴다. **이번 평가의 지원은 "러너 정답 기반 oracle 층화 지원"으로 확정한다**: 러너 로그의 정답으로 보류 서버 학습 단계에서 클래스·구현별 처음 3/5개를 골라 주며, 그 지원을 찾기 위해 사람이 추가로 읽는 라벨 조회량은 예산에 넣지 않는다. 따라서 "실제로 N개를 읽어 찾은 경우"와 다른 조건이며 그 해석을 하지 않는다(필요하면 별도 조건으로 후속).
- **특징 선택 규칙(탐색용 고정값, 시험 점수로 바꾸지 않음)**: 유효 후보 칸 = **지원을 추가하기 전의 원 서버 학습 행만으로 계산한** 분산이 0이 아닌(마스킹 후) seq 앞 k칸. 각 칸마다 **원 서버(두 학습 서버) 학습 행으로 깊이 1 스텀프**를 학습하고 **지원 행의 균형 정확도**로 순위를 매겨 **상위 r칸 유지**(k=5: r=2, k=10: r=4, k=15: r=6). 동률은 원 서버 학습 정확도 → 열 번호 순. 선택된 칸 목록을 폴드·N별로 보고한다. r과 N은 최적이라는 근거가 없는 실행 예산 기반 값이며, 12/20 라벨에서 순위 변동과 다중비교 불안정이 남는다.
- 후보 정의는 **마스킹 적용 후**의 열이다. 후보 수 < r이면 후보를 전부 유지한다(선택이 개입하지 않음). 동률 규칙은 위와 같다.
- **k=5 + 마스킹**은 후보가 seq_3·seq_4 두 칸뿐이고 r=2라 선택이 실제로 개입하지 않으므로 요인 B는 "효과 없음/식별 불가"로 보고한다.
- 해석 한정: B019식 지름길 제거에 대응시킨 시도이며 재현이 아니다.
- **지원 선택 민감도 분석(개정 5a, 탐색)**: 주 분석은 "처음 N개"를 유지한다. 별도 민감도로 보류 서버 학습 단계에서 서로 겹치지 않는 지원 창을 만들어 같은 시험 행으로 반복 평가한다. **평가 전에 고정**: 창 수 = 구현별 로그인 9칸 회전이 한 바퀴(9라운드)가 되는 창을 기본으로 하고 9라운드 미만이면 사용하지 않는다(3라운드 창은 로그인 9칸 중 3칸에 실패 전용 정상이 0건이라 회전 한 바퀴가 아닌 창의 구성 차이와 지원 선택 효과가 섞인다), 창 경계는 라운드 경계, 시험 단계보다 600초 이상 앞섬, 지원이 부족하면 그 창은 제외하고 수를 보고, 반복 수·시드는 시험 점수를 보기 전에 기록. 같은 시험 행·겹치는 학습을 쓰는 반복은 **독립 표본이 아니다.**
- **신뢰구간(개정 5a)**: 시간·라운드 블록 의존성을 반영한 블록 부트스트랩(블록 = 라운드, 시드 고정)을 우선하고, 연결 단위 부트스트랩은 독립 가정의 탐색값으로만 보고한다. 조건 간 차이는 같은 지원·같은 재표집을 쓰는 **paired 차이 신뢰구간**으로 평가하며 "개별 신뢰구간 폭보다 작다"는 규칙으로 유의성을 판단하지 않는다.
- **고정 세부(개정 5b, 본 수집 데이터를 보기 전에 고정)**:
  - **지원 창**: 보류 서버의 학습 단계 라운드 1~9, 10~18, 19~27(겹치지 않는 9라운드 3개, 28~30은 쓰지 않음). 각 창에서 지원 = 시작 시각 순서로 클래스별·구현별로 처음 3(N=6) 또는 5(N=10)개. 창 안 후보가 부족하면 그 창을 제외하고 제외 사실을 보고한다. 모든 창은 시험 단계보다 600초 이상 앞선다(시험 직전 660초 대기로 보장, 감사 대상).
  - **주 분석과 민감도 분석의 구분**: 주 분석은 창 1(라운드 1~9)의 지원만 쓴다(= "처음 N개"와 같음). 창 2·3은 민감도 분석으로만 보고하며 주 결과를 고르는 데 쓰지 않는다. 지원이 시험 점수로 선택되는 일은 없다.
  - **반복**: 모델 난수 시드 3개(0, 1, 2) × 지원 창 3개 = 조건당 9회. 시드는 모델 난수만 바꾸므로 독립 표본으로 세지 않고, 보고는 창별 값(시드 평균)과 창 간 범위로 한다.
  - **블록 부트스트랩(주 CI)**: 보류 서버(폴드)별 시험 단계의 라운드 10개를 블록으로 복원추출 2,000회, 난수 시드 20261109. 폴드마다 따로 하고 폴드 간 합산 값은 같은 반복 번호의 재표집을 합쳐 계산한다. 신뢰구간은 퍼센타일 95%. 블록이 10개뿐이라 구간이 거칠다는 한계를 함께 적는다.
  - **paired 차이 CI**: 두 조건의 차이는 같은 지원·같은 재표집(같은 라운드 인덱스)에서 계산한 차이의 퍼센타일 95% 구간이다. 0을 포함하면 "차이가 있다고 말하지 않는다".
  - **연결 단위 부트스트랩(탐색값)**: 같은 시드·횟수로 연결을 복원추출하되, 독립 가정이 깨져 있으므로 보조 표에만 두고 주 결론에 쓰지 않는다.
  - 위 값은 평가 중 바꾸지 않는다. 바꾸면 변경 기록에 사유를 남기고 변경 전 결과도 보고한다.

### 4.3 조기성 지표 (탐색, 고정 k 실험이 기준선)
- 연결 시작→k번째 payload 패킷까지의 시간(`t_k5`, `t_k10`, `t_k15`, `match` 출력 CSV)은 **관측 대기시간**이며 모델 처리시간과 구분한다. 공격 시작→판단 시간은 공격 시작을 로그·패킷에 대응시킬 수 있을 때만 보고한다.
- k별 미도달률(그 k개 payload 패킷에 도달하지 못한 연결), 실제 판정 분모, 정상 FP 건수를 함께 낸다.

### 4.4 단계적 판정 정책 (탐색, 기권 허용)
- 목표: 오탐을 제한하면서, 탐지 가능한 공격을 최대한 이른 시점에 탐지한다. 정보가 부족하면 판단을 보류하고 추가 관측한다. (판단 시점 선택은 TEASER 연구가 관련 연구 후보이다. 원문 초록의 "주기적 분류"와 "판단 신뢰성을 평가하는 두 번째 분류기"만 확인했고 본문·TLS 적용 가능성은 검토하지 않았다. 우리 정책이 이를 재현하거나 같은 성능을 낸다고 쓰지 않는다.)
- 앞 5개: 검증된 경보 조건을 만족하면 공격 경보, 아니면 관측 계속. 앞 10·15개: 추가 정보로 재평가. 최대 관측(30개 payload 패킷 `seq_29`) 또는 연결 종료: 최종 판단하되 끝까지 근거가 부족하면 **미판정**으로 둔다. 연결이 중간에 끝나 지정 단계(5·10·15·20·30)에 도달하지 못하면 **마지막으로 도달한 지정 단계까지만 평가**하고 미등록 패킷 수에서 새 판단을 하지 않는다. 판정에 쓰인 관측 수를 기록한다.
- 경보 조건은 모델 확률이 높다는 이유만으로 정하지 않는다(새 환경에서 자신 있게 틀린 사례). **학습 fold 안에서도 에피소드·시간 블록을 분리한 검증 예측**으로, 5→10→15→20→30 다섯 단계 전체 정책의 누적 FP와 탐지율(지표도 다섯 단계 전체)을 함께 계산해 고르고, 시험에서는 조건을 고정한다.
- 분모와 기록: 탐지율의 분모는 미판정 공격까지 포함한 **전체 공격 연결**이다. 한 번 경보한 정상 연결은 나중에 판단을 바꿔도 **누적 FP로 남긴다**. 오탐을 줄이려고 대부분을 미판정으로 남기는 정책과 구분하기 위해 단계별 판정 비율·미판정 비율을 함께 보고한다. 더 기다린다고 오탐이 반드시 줄어드는 것은 아니며 그것도 결과로 보고한다.
- **누적 FP 범위**: 단계적 정책의 최종 30개 판단과 연결 종료 시점 판단도 누적 FP 계산에 포함한다. 최대 대기시간과 정상 판정 조건은 평가 전에 확정한다.
- **정상 판정**: 경보하지 않았다고 정상은 아니다. 이번 평가는 5·10·15(·20·30)개에서 "공격 경보 또는 보류"만 판단하고, 검증된 정상 판정 조건이 생기기 전에는 정상 판정을 쓰지 않는다. 끝까지 경보가 없으면 **미판정**이다.
- **경보 이후**: 첫 경보를 내면 그 연결의 탐지를 종료하되 이후 관측은 로그로 남긴다. 나중에 판단이 바뀌어도 최초 경보 이력과 오탐 기록은 보존한다.
- **관측 종료(Codex 확인 필요한 제안값)**: 재평가 시점 5·10·15·20·30, 최대 관측 = 30개 payload 패킷 또는 연결 종료 중 먼저 오는 쪽. 시간 측정 시작점 = pcap에서 그 연결의 첫 패킷(`start_ts`). 초 단위 상한은 완료된 연결의 오프라인 실험에서는 두지 않는다. **실시간 대시보드에서는 "분석 중"이 무한히 남지 않도록 유한한 시간 제한이 필요**하며 그 값은 대시보드 단계에서 정한다.
- **미판정**: 이유를 "30개 미만 종료"(연결이 30개 payload 패킷 전에 끝남)와 "30개 관측 후 기준 미충족"으로 구분해 기록하고, **캡처 종료로 잘린 연결은 실제 연결 종료와 구분**해 표시한다. 미판정은 정상도, 미지 공격을 발견했다는 뜻도 아니다. 미판정 공격은 미탐으로 집계하고 미판정률과 사람의 검토 부담(연결 1,000개당 경보·미판정 건수)을 함께 보고한다. 미판정이 너무 많아 탐지기로서 쓸모가 없어지는지도 검증 대상이다.
- **대시보드 동작(합의 중인 설계, 구현·검증 안 됨)**: 조기 경보 조건을 만족한 연결은 뒤 패킷을 기다리지 않고 즉시 "공격 의심"으로 알린다. 근거가 부족하면 "분석 중"으로 표시하되 공격 경보와 구분한다. 최대 관측 도달·연결 종료 시 공격 의심 / 미판정으로 표시한다.
- 주 표에 **단계별 도달 분모**(그 단계 payload 패킷 수에 도달한 연결 수)를 함께 낸다. 파일럿에서 payload 20개 도달은 35%, 30개 도달은 1.7%다. **20~29개로 끝난 연결은 단계 20 판단까지만 유효**하고(미등록 패킷 수에서는 새 판단을 하지 않음) 단계 30은 도달한 연결만으로 평가한다. 짧은 연결을 0으로 채운 고정 길이 오프라인 진단(k=30 RF)은 단계 30 도달 연결의 조기 판정 성능과 다르므로 섞어 해석하지 않는다.
- 지표: 최종 탐지율·오탐률, 5/10/15개에서 판정한 비율, 관측 대기시간, 끝까지 미판정인 비율, 단계별 FP와 연결 단위 누적 FP.

### 4.5 구현 하나 빼기 (탐색, 두 방향)
- 학습 구현의 **학습 단계**로 학습하고 보류 구현의 **시험 단계**로 시험한다(requests→curl, curl→requests). 서버 구성·표본 수·클래스 비율을 맞추고, **주 대조는 무지원**이다.
- 이 결과는 구현 간 전이의 근거이며, 모델이 행동을 학습했다는 것을 직접 입증하지는 않는다. 구현 간 차이가 가장 큰 구간은 k=5(curl은 요청이 앞 패킷에 들어오지 않을 것이라는 가설)이므로 구현별 값을 따로 보고한다.


## 5. 한계
실험실 트래픽은 단순하고 도구 2종·서버 구성 3개(노트북 1대 포트 3개)·공격 한 유형·같은 앱·한 LAN이다. LOSO는 3회뿐이다. 클라이언트 OS가 하나라 기기·OS 변화는 시험하지 못한다. requests/curl이 TLS 구현의 서명이 될 수 있어 두 구현을 정상·공격 모두에 쓰지만 구현 효과가 완전히 제거되지는 않는다. S3(RSA-4096 2단 체인)는 서버 첫 비행이 여러 세그먼트로 갈릴 수 있고(추정, 파일럿 확인), LAN/오프로드로 세그먼트 구성이 loopback과 달라질 수 있다. 서버 시계와 러너 시계가 달라 시각 매칭에 의존한다. 정상 대표성은 확보되지 않았다. 폴드 3개로는 서버 간 분산을 추정할 수 없고, 실패 전용 부분집합은 서버 시험당 정상 40행(구현당 20)이라 FP 0건이어도 Wilson 상한이 약 16%다.

## 6. 구현 상태 (b/collect)
구현됨(loopback 검증, 테스트 8개): 러너·오케스트레이터(쿼터·배정표·쿠키 끔·curl `--next`·재수행/중단·메타데이터·로그 새 파일 전용), 서버 수락 로그(`hs_fail` 포함·TCP_NODELAY), 수락 판정 강화(상태·인증 결과·curl 종료 코드),
`match`(모호 분리·(단계,서버)별 offset·구현별/라운드별 잔차·시험 간격 검사·쿼터 검사 강화·칸별 손실·pcap skipped·`payload>1460`(MSS)·`t_k5/10/15`·파일럿 합격 판정 출력).
미구현/미확정:
1. 첫 HTTP 요청의 패킷 위치를 서버 요청 시각과 대응시키는 방법(서버가 요청 시각을 기록하지 않음). 현재는 후보 방법(`first_request_index`)이며 확정이 아니다.
2. 응답 길이 단서(성공 응답) 처리: 맞추지 않고 잔존 한계로 보고(위 1절).
3. 요청 간격 중앙값 차이: 합격 판정에서 보고로 바꿈(1절). S3 첫 비행 세그먼트 수 보고는 파일럿 분석 스크립트에서.
4. 평가 스크립트(교락/혼합, 2×2, 스텀프 선택, 단계적 판정, 구현 하나 빼기)는 수집 후.
5. LAN 파일럿 1 완료(`docs/track_b_collect_pilot1.md`, 합격 4개 통과). 개정 5 코드(실패 전용 회전, git·SHA 메타데이터, 판정 `extra_ok`·`clean_ok`·`round_clock_ok`)는 **파일럿 2(학습 3·시험 2)로 지름길이 사라졌는지 확인한 뒤** 본 수집한다. 본 수집 직전 두 PC에서 `w32tm /resync`를 하고 실행 중 시간 동기화를 끄며 전후 `w32tm /query /status`를 기록한다.
